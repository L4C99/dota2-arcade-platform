# P-1 玩家原型

本目录是只使用虚构数据的静态原型，不连接 API、节点或 d2core。三个方案使用同一产品语义：选择游廊游戏与玩法 → 默认自动节点 → 申请服务器；手动节点收在高级选项中。页面顶部的“已有申请”用于预览同一 owner 存在活动申请时的优先展示状态，所有按钮只改变本地视觉状态。

A 方案的“全部地图”“游戏模式”仅是玩家界面标题，分别对应冻结规格中的 `ArcadeGame`（游廊游戏）和 `GamePreset`（玩法预设）；没有新增地图或模式实体。

项目所有者已确认 **A · 舒展卡片** 的当前桌面端与手机端视觉稿为 P-1A 定稿，作为后续玩家页面的视觉与信息架构方向。B/C 保留为本轮比较稿；本次确认不授权进入 P-1B。

| 方案 | 信息层级差异 |
| --- | --- |
| A · 舒展卡片 | 游戏和玩法各自成卡，队伍与节点摘要放在申请卡旁，适合先浏览再决定。 |
| B · 编辑式单栏 | 游戏、玩法、节点按顺序纵向排列，申请路径最直接。 |
| C · 双栏工具式 | 左侧完成选择，右侧持续展示队伍、节点与申请摘要，信息密度略高。 |

## 本地查看

直接用 Chrome 或 Edge 打开 `index.html`，顶部可切换 A / B / C。也可在本目录运行 `python -m http.server 8000`，再访问 `http://localhost:8000/`。无需安装依赖。

P-1A 页面中的游戏、节点、容量和延迟均为虚构示例；没有真实 IP、域名或部署参数。全局维护提示、内容维护提示、四种节点可用状态与活动申请状态均为视觉示例。P-1A 定稿页保持原样，P-1B 正常流程另见下方页面。

## P-1B 玩家正常流程

打开 [flow.html](flow.html) 查看基于已定稿 A 方案扩展的正常流程原型。选择地图、游戏模式及自动/手动节点后提交申请；顶部演示栏可依次模拟节点受理、服务器就绪及完整回收。页面展示等待、启动、Ready、手动 `connect`、一键进入、结束和下一局。纯 waiting 且尚未分配时可演示安全取消。

一键入口、节点状态、连接地址与复制内容均为模拟示例，不会启动 Steam 或连接服务器。原型以“已真人验证并启用的 Steam 入口”和“未验证的蒸汽平台入口”展示开放条件；正式产品必须按冻结规格检查真实 verified/enabled 及 JoinInfo。下一局演示为先完整回收、再创建新申请，不调用实例 restart。

手动进房帮助只展示控制台使用路径；Dota 2 客户端中的具体设置位置和默认键位尚未在真实客户端复核，不作为最终帮助文案。此页没有 API、持久化、真实轮询或 d2core 集成；P-1C 队伍与异常、P-1D 管理员原型均未开始。
