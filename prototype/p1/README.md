# P-1 玩家原型

本目录是只使用虚构数据的静态原型，不连接 API、节点或 d2core。三个方案使用同一产品语义：选择游廊游戏与玩法 → 默认自动节点 → 申请服务器；手动节点收在高级选项中。页面顶部的“已有申请”用于预览同一 owner 存在活动申请时的优先展示状态，所有按钮只改变本地视觉状态。

A 方案的“全部地图”“游戏模式”仅是玩家界面标题，分别对应冻结规格中的 `ArcadeGame`（游廊游戏）和 `GamePreset`（玩法预设）；没有新增地图或模式实体。

项目所有者已确认 **A · 舒展卡片** 的桌面端与手机端视觉稿为 P-1A 定稿，作为后续玩家页面的视觉与信息架构方向。B/C 保留为比较稿。

| 方案 | 信息层级差异 |
| --- | --- |
| A · 舒展卡片 | 游戏和玩法各自成卡，队伍与节点摘要放在申请卡旁，适合先浏览再决定。 |
| B · 编辑式单栏 | 游戏、玩法、节点按顺序纵向排列，申请路径最直接。 |
| C · 双栏工具式 | 左侧完成选择，右侧持续展示队伍、节点与申请摘要，信息密度略高。 |

## 本地查看

直接用 Chrome 或 Edge 打开 `index.html`，顶部可切换 A / B / C。也可在本目录运行 `python -m http.server 8000`，再访问 `http://localhost:8000/`。无需安装依赖。

P-1A 页面中的游戏、节点、容量和延迟均为虚构示例；没有真实 IP、域名或部署参数。全局维护提示、内容维护提示、四种节点可用状态与活动申请状态均为视觉示例。P-1A 定稿页保持原样，P-1B 正常流程另见下方页面。

## P-1B 玩家正常流程

打开 [flow.html](flow.html) 查看基于已定稿 A 方案扩展的正常流程原型。选择地图、游戏模式及自动/手动节点后提交申请；顶部演示栏可依次模拟节点受理、服务器就绪及完整回收。页面展示等待、启动、Ready、手动 `connect`、一键进入、结束和下一局。纯 waiting 且尚未分配时可演示安全取消。

一键入口、节点状态、连接地址与复制内容均为模拟示例，不会启动 Steam 或连接服务器。原型以“已验证并启用的 Steam 入口”和“未验证的蒸汽平台入口”展示开放条件；正式产品必须按冻结规格检查真实 verified/enabled 及 JoinInfo。下一局沿用当前地图、模式和节点方式，先完整回收、再创建新申请并重新排队，不调用实例 restart。

手动进房帮助参考项目所有者提供的现用平台说明，使用 Steam 中 Dota 2 的启动选项 `-console`，不包含与控制台无关的 `-perfectworld`。具体设置路径和控制台按键尚未在真实 Dota 2 客户端独立复核，不作为最终帮助文案。此页没有 API、持久化、真实轮询或 d2core 集成。

## P-1C 队伍与异常

打开 [party.html](party.html) 查看队伍、邀请及异常状态原型。顶部演示栏可切换未入队、收到邀请、队长/队员、状态未知、异常隔离和“下一局”回收异常场景。演示队长创建/解散队伍、复制/重置邀请链接、队员加入/退出，以及队长在异常隔离后经二次确认“放弃此异常服务器并继续”。

状态未知时不提供放弃入口，也不重新创建或改派；异常隔离后旧申请与资源记录保留，旧节点容量继续占用。普通放弃只解除阻塞，随后由队长重新选择并申请；若下一局意图已暂停，放弃后才创建新的等待申请。所有队伍、邀请地址和异常状态均为模拟数据，不连接 API，也不影响真实资源。展示的 `example.invalid` 链接不是正式邀请凭证；正式产品必须使用不可猜测的高熵邀请链接。P-1D 管理员原型尚未开始。
