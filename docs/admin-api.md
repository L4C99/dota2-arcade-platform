# Administrator API (P4D, P5 automation)

The administrator UI is served at `/admin` and uses same-origin `/api/v1/admin`. Its cookie is separate from the anonymous player Session. Production requires HTTPS; the cookie is `Secure`, `HttpOnly`, `SameSite=Lax`, host-only and expires absolutely after 12 hours. A successful login issues a fresh opaque token and revokes the previous token in that browser. Logout revokes immediately; disabling an AdminUser or resetting its password invalidates existing sessions through the server-side credential version. Login failures use an IP + normalized username exponential backoff. Mutating requests require the configured exact Origin; wildcard CORS is not enabled. The backend authenticates the AdminUser on every request.

| Method | Route | Purpose |
| --- | --- | --- |
| POST | `/login` | Username/password login; Argon2id verifier in PostgreSQL |
| GET | `/me` | Check independent AdminSession |
| POST | `/logout` | Revoke current AdminSession |
| GET | `/overview` | Sanitized settings, catalog, Node and binding facts, entry state, recent requests/Allocations/open jobs, Party summary and Audit |
| POST | `/actions` | Typed administrative state transition, authorized and audited in one database transaction |

`POST /actions` accepts an `action` and the fields for that action. Supported actions: `global.update` (`accepting`, `message`), `announcement.update` (`message`), `game.update` / `preset.update` (`targetId`, `enabled`, `accepting`, `message`), `node.update` (`targetId`, `draining`, `priority`, `desired`), `binding.update` (`targetId` Node, `gameId`, `accepting`), `node.reconcile` (`targetId`), `request.cancel` (`targetId`), `request.stop` (`targetId`), `allocation.quarantine` (`targetId`), and `entry.update` (`targetId` Node, `entry=steam|steamchina`, `verified` or `enabled`, with `confirmed=true` for a new human verification). Invalid state transitions return 409; malformed actions return 400. Unknown JSON fields are rejected.

P5 adds `game.create` (`workshopId`, `displayName`), `template.create` (`targetId` game, `templateRevisionId`, `description`), `content.create` (`targetId` game, `contentVersionId`, `contentSha256`), `preset.create` (`targetId` game, `displayName`, `maxPlayers`, `templateRevisionId`), and `template_binding.upsert` (`targetId` node, `templateRevisionId`, `bindingKey`). New games and presets start disabled and not accepting requests. `ContentVersion` is immutable. The binding key is a Controller-local logical name, never a Web-supplied path.

`content.validate` (`targetId` node, `gameId`, `contentVersionId`, `confirmed=true`) records an administrator's human validation only after the node is drained and empty and a fresh compatible Controller report confirms the matching version and VPK SHA256. It does not set Controller-reported facts. `content.publish` (`targetId` game, `contentVersionId`, `confirmed=true`) requires a prior validation on a resumed, currently compatible node whose reported digest still matches the immutable version. The node's binding may still have `accepting_new_allocations=false`: publish changes the target first, then the operator separately opens binding admission. Publication changes only the game's target for future Allocation attempts, and audits the prior and new targets. Waiting requests snapshot the target when allocated; existing Allocations are never rewritten. Neither action changes node files or creates a validation instance.

`node.update` cannot set desired capacity above the Controller-reported hard limit. `binding.update` changes only Platform admission; it cannot change reported content version/state/time. Under [V1.0 Amendment 001](specs/v1-amendment-001-entry-verification.md), `entry.update` human verification requires the target Node, `entry=steam|steamchina`, `verified=true`, and `confirmed=true`. The trusted administrator confirms that a real client entered a real Ready instance through that scheme's URI on the current entry configuration revision. Port lists and verification notes are not API fields. In one revision verification is monotonic: `verified=false` is rejected as an Admin action; a duplicate confirmation conflicts. `enabled=false` is the routine closure and preserves verification metadata; `enabled=true` requires verified. Only a changed Controller network revision clears both schemes' verification, enabled state, time and actor. A2S diagnostics do not change these states or player URI exposure. Migrations 15 and 17 remain historical; migration 18 adds per-instance diagnostics without rewriting them.

`GET /overview` exposes `a2sEnabled` as a Node deployment fact and attaches optional `instanceId`, `a2sLocalPort`, `a2sStatus=ok|failed`, and `a2sCheckedAt` to current Allocation records. A running Allocation with an instance ID but no A2S status has no current query fact; it is not a failure. The legacy aggregate `a2sQueryOk` remains in Node heartbeat/storage only for compatibility and is omitted from the Admin Entry state. No A2S field is returned by the Player API or JoinInfo.

`request.cancel` requires a pure waiting request with no Allocation. `request.stop` creates a normal stop NodeJob for a trusted existing instance and retains capacity until full d2core reclaim. It also permits an already abandoned request when its old Allocation remains quarantined; the request stays abandoned, the old history is retained, and only confirmed full reclaim releases that old capacity. An open stop Job or an already reclaimed Allocation rejects another stop. `allocation.quarantine` preserves capacity, old node/port/content and history; it rejects a pure pending reservation. `node.reconcile` queues a durable generation for the target Controller; completion means a pass was attempted, not that all problems disappeared.

Audit records the administrator identity, action, target, time and relevant prior/resulting state without password, Session token, Node Secret, SSH key, frozen local path or raw private network facts. CLI operator actions and automatic unreachable quarantine use their own actor kind. `/overview` omits raw network facts and local paths, and shows only structured error codes. No Web shell, arbitrary console/command, process kill, file browser, firewall or NAT control exists.
