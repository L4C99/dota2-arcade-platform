## H-01 — CLOSED

修订规格 [§12](v1.0.2-content-maintenance-validation.md#12-node-api-v1--controller-兼容合同) 和 §16 将 required capability 设为新 create/stop Job **持久且不可降级**的属性，已 prepare 的 frozen execution 继承要求。§12 明确排除“共享 Node 凭据或上次 heartbeat 等于本次调用者能力”的推断，要求当前 Controller 进程/会话有经认证且有效的逐请求证明。

Fence 明确覆盖 `/jobs/open`、普通及 independent-stop claim、GET job、prepare、恢复读取、report、active-allocation 和 instance-fact。无能力的列表要过滤新 Job/Allocation 与 frozen payload，按 ID 访问及状态写入要拒绝；不能依赖旧 binary 自行忽略。§13 明确覆盖“新 Controller 冻结后崩溃、旧 binary 接替”的原始漏洞。能力暂缺保持原 Job、unknown 状态与容量；有能力者返回后沿同一 Job、key、path/port/指纹恢复。旧 Controller 仍可取得、恢复、执行、报告 legacy Job。若逐请求隔离无法以真正 additive 的 Node API v1 实现，§12 强制协议升级和兼容迁移。§20 增加了 frozen create/stop → 旧 Controller → 新 Controller 的混版恢复验收。

这些是足以指导实施和验收的安全合同；具体会话或认证机制留给实现阶段，没有在本轮预设。

## H-02 — CLOSED

修订 [§15](v1.0.2-content-maintenance-validation.md#15-并发锁顺序与原子性) 正面指出原有 `request.stop` 的 Request→Allocation 与报告的 Job/Allocation→Request 反序，并废弃“报告只需局部 Job→Allocation”的旧表述。统一顺序为 **ServerRequest → 公共设置/目录/Node/Binding → NodeJob → Allocation → NextGameIntent**；不参与的对象可跳过。所有 player-owned 报告、对账、stop 等事务须先锁 ServerRequest，再锁相关 Job，再锁 Allocation；Validation 没有 Request，走 Job→Allocation。

§15 逐名覆盖 `ReportJob`、`ReportInstanceFact`、`request.stop`、next-game stop、Admin stop/terminate/quarantine、自动 stop、quarantine/reclaim。允许无锁查关联 ID，再按正式顺序加锁并重新核对 owner、Job、Allocation、instance 及状态；禁止持有 Job/Allocation 后反向取得 Request，也禁止 Allocation→Job。状态推进与 stop Job 建立保持同一事务，open-stop 唯一约束、固定 create key、unknown/quarantine、完整 reclaim 后才释放容量均保留。§20 的 PostgreSQL 验收要求强制交错 `request.stop` 与两条报告路径的 quarantine、reclaim、stop 转换，并覆盖 next-game/Admin stop，检查死锁、重复 stop、终态丢失和不安全容量释放。这直接覆盖上一轮的死锁 finding。

## M-01 — CLOSED

修订 [§10](v1.0.2-content-maintenance-validation.md#10-受控未来模板指针与发布记录) 的“旧内容动作边界”明确规定：只有**全部现存 Preset 仍为 `legacy_v1` 且从未完成首次 v1.0.2 release** 的游戏可走旧 `content.validate` / `content.publish`。任一玩法进入 `v1_0_2`（含新建玩法）或首次 release 完成后，两入口对该游戏均拒绝；此后的正式 ContentVersion/TemplateRevision 切换只能走 `release.publish`。§16 要求旧动作在数据库事务内守卫，旧 `content_release_validations` 永不转成 ValidationRun PASS，`validation_contract` 不可降回 legacy。§20 增加了升级/legacy 两侧的 API 验收。由此不存在旧入口改正式指针或复活旧准入的合同漏洞。
