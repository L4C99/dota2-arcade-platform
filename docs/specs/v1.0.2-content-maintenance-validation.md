## 1. 覆盖范围与不可变边界

从 **v1.0.2 功能完成并发布后**，本文取代 V1 §21.1、§21.2–21.4、§36 与 §45 中关于“日常 VPK/新图内容验证实例必须在整 Node Drain 窗口由人工直接调用 d2core、整节点 occupied=0、按 Node+Game+ContentVersion 手工确认即足以发布”的规则。V1 对历史 v1.0.1 操作的记载不回写为新规则。Dota/App570、d2core binary/protocol、Controller 重大升级、OS/内核/重启和整机硬件维护继续采用 Node 级维护；本文不授权无停机处理这些事项。

继续严格遵守：`ServerRequest != Allocation != NodeJob != d2core instance`；玩家 owner 的单一 blocking Request、顺序 Allocation attempts、不可变历史快照；同一 NodeJob 固定 key 与首次 core 调用前冻结执行；unknown 不等于失败；FIX-05 禁止已发出且结果 unknown 的 create 被“无副作用”推断释放；quarantine 持续占容量；accepted 实例仅在 `lifecycle=reclaimed && process=stopped && cleanup=complete` 后释放。正常业务与验证均不调用 core instance `restart`。Player Web、Content Tool、Dota 客户端控制流程与固定 d2core 不在本版本改动范围。

**版本隔离仍为 Node × ArcadeGame 的单一当前内容视图。**本规格允许同 Node 的另一 ArcadeGame 活跃，不允许目标游戏旧 VPK 实例与新 VPK 实例并行、切换其活动实例下的内容链接或实现 per-instance VPK 隔离。Content Tool 仍由运维显式调用，不自行 Drain，也不由 Controller 自动调用。

## 2. 现状依据与变更原因

当前 `TryAllocateOne` 先锁 waiting `ServerRequest`，再 `FOR SHARE OF s,g,p` 读取全局、游戏、玩法，随后 `FOR UPDATE` 锁 Node 并通过 `nodeEligibilitySQL` 读取 NodeContentBinding 和容量；Allocation 快照 `content_version_id`、`template_revision_id`，同事务插入普通 create NodeJob。`occupied` 是本 Node 未 `reclaimed`/`released_no_effect` 的 Allocation 数。`integration_only` Job 无 Allocation，不计容量。现有 `content.validate` 要求 Node Drain 和整 Node `occupied=0`，其表只键入 Node/Game/ContentVersion，不记录模板、实例与真实回收；`preset.update` 不能切换模板。见 [allocation.go](../../internal/platform/store/allocation.go)、[node_eligibility.go](../../internal/platform/store/node_eligibility.go)、[capacity.go](../../internal/platform/store/capacity.go)、[admin_actions.go](../../internal/platform/store/admin_actions.go)、[0004](../../internal/platform/store/migrations/0004_p1a_catalog_requests.sql)、[0005](../../internal/platform/store/migrations/0005_p1b_allocations.sql)、[0014](../../internal/platform/store/migrations/0014_p5a_content_publication.sql)。

固定 d2core 的 `readiness.successAll` 对**本代** `engine.log` 作字面字符串匹配；全部成功规则命中且进程存活才可能 Ready。新 VPK 可能改变日志或启动语义，使旧 TemplateRevision 不再兼容。不能以删除缺失 marker、只测端口或把 `loading` 当 Ready 代替真实启动/进服证据。旧模板应先与新 VPK 实测；确证其启动语义不适用时，再创建 t2 并重新验证。d2core 的具体解释见固定 tag 的 `internal/engine/observe.go` 与 `examples/README.md`，不取其 `main` 行为。

## 3. 正式组合、候选与逐玩法覆盖

正式未来组合按现有对象表达：`ArcadeGame.current_content_version_id` 是新 Allocation attempt 的内容目标；每个 `GamePreset.template_revision_id` 是该玩法新 attempt 的模板目标。候选是已登记的不可变 ContentVersion、TemplateRevision 与特定 Node/玩法的 ValidationRun，不改变正式指针。waiting ServerRequest 不快照版本；真正创建 Allocation 时在同一事务取当前内容和模板，旧 Allocation 永久保留自己的 `node_id + content_version_id + template_revision_id`。

一张游戏可以有 P1 候选 `(v2,t2)` PASS、P2 尚未验证。发布 v2 时，P1 可以使用 t2 并开放；P2 必须保持 `accepting_new_requests=false`，其 waiting Request 保留队列时间并暂停调度。发布事务不得把 P1 的证明算作 P2；即使两个玩法引用同一个 TemplateRevision，也需每个要开放的 `GamePreset` 有自己的真人 ValidationRun。P2 随后可验证 `(v2,t1)` 或 `(v2,t2)`，通过受控发布/开放动作加入服务。一个 Node 对 P1 有证明，不代表其它 Node 或 P2 有证明。

由于 ValidationRun 前的 scoped gate 排空的是该 Node 上**整张目标游戏**，若先在 Node A 开放 P1，日后又要在 A 验证 P2，必须重新关闭 A × Game、等待包括 P1 在内的该游戏当前实例正常结束，再开始新的维护代次；新代次使 A 上旧 P1 准入证明失效，重新开放 P1 也需要本代次的 P1 PASS。Owner 可在同一关闭窗口逐个验证 P1、P2 并逐个发布，或用另一台已排空的 Node 验证 P2；这不影响其它 ArcadeGame。

对已进入 v1.0.2 验收合同的玩法，正常调度必须同时匹配：正式内容/模板指针、Node 报告的准确内容版本与 SHA、Node 模板绑定及实际指纹、该 **Node × GamePreset × ContentVersion × TemplateRevision** 的有效 PASS 证明、NodeContentBinding admission，以及原有全局/游戏/玩法/节点/容量门槛。证明因维护代次、内容事实或模板身份改变而失效时，即使管理员误打开开关，调度也必须拒绝。

## 4. ValidationRun 数据合同

`ValidationRun` 是管理员发起的一次不可替代的验证意图，不是玩家 ServerRequest。每次 Run 固定以下身份与输入：

| 字段/关系 | 冻结语义 |
| --- | --- |
| `id`、`created_at`、`started_by_admin_user_id` | 唯一 UUID、Platform UTC 创建时间、已认证发起者；均不可重指派。 |
| `node_id`、`arcade_game_id`、`game_preset_id` | 指定单一 Node 和属于该游戏的单一玩法；游戏/玩法归属用复合 FK 验证。 |
| `content_version_id`、`content_sha256` | 候选不可变 ContentVersion 及其登记 SHA256 的快照；必须与 Controller 实测 VPK digest 相同。 |
| `template_revision_id`、`template_binding_key`、`template_fingerprint_sha256`、`template_binding_generation` | 候选逻辑模板、该 Node 的绑定身份与机器可验证文件/依赖指纹；变更后旧 Run 不代表新绑定。 |
| `maintenance_epoch`、`content_fact_revision`、`template_fact_revision` | 目标绑定的本次维护代次及 Controller 内容/模板最终事实代次；防止切换离开后又切回相同字节时旧 PASS 被自动复活。 |
| `state`、`failure_code`、`result_code`、`created_at`/关键状态时间 | 结构化生命周期与最小验证结果；失败不得覆盖为另一尝试。 |
| `human_result`、`human_confirmed_by`、`human_confirmed_at` | `pending/pass/fail`、执行确认的 AdminUser 和 Platform UTC 时间。`pass` 是可信管理员对 **Owner 真人使用该 Run 的 JoinInfo 进入并确认玩法** 的审计声明；没有自动侦测玩家的含义。 |
| `ready_at`、`join_info_available_at`、`passed_at` | 分别由可信 core/Controller 报告、有效 JoinInfo 与最终 PASS 门槛产生；不能以页面时间伪造。 |
| Allocation / create Job / stop Job / instance | `allocations.validation_run_id` 唯一 FK 形成一对一资源预留；其 NodeJob 链提供唯一 create、可顺序重试的 stop 历史及 create Job 的可信 `instance_id`。Admin 详情必须返回这些关联 ID，避免冗余可改写副本。 |

Run 的候选身份、绑定快照和维护代次一旦提交即不可改；状态及实际证据只可按第 6 节单调推进。失败后重验必须创建新的 Run、Allocation、create Job；可安全重试 stop 的场景沿原 Allocation/instance 创建新的顺序 stop Job，不能创建第二个 create。历史 Run、Job、审计与失败原因永久保留。原始私有日志不上传 Platform。

## 5. Allocation purpose 与容量合同

Allocation 增加 `purpose IN ('player','validation')`，旧行全部回填 `player`。数据库级 owner XOR：

```text
purpose = player     ⇔ server_request_id IS NOT NULL AND validation_run_id IS NULL
purpose = validation ⇔ server_request_id IS NULL     AND validation_run_id IS NOT NULL
```

`validation_run_id` 唯一；验证 Allocation 的 `attempt_sequence=1`，Node/Game/Content/Template 与 Run 一致并受不可变触发器保护。已有 `(server_request_id, attempt_sequence)` 唯一与玩家单 active attempt 约束保持；验证没有玩家 owner、玩家排队、next-game intent 或 Player API 可见连接入口。NodeJob 仍 `integration_only=false` 且 `allocation_id` 非空，沿现有一 Allocation 一 create、至多一 open stop 的索引与领取冲突谓词。现有 `integration_only` 仅保留历史 P0 集成路径，**绝不用来执行 ValidationRun**。

正式 `occupied`、调度资格、Admin 容量与 desired/hard 上限都统一计数两种 purpose 的所有非资源终态 Allocation。reserve 事务必须锁 Node、复查 `occupied < min(hard_max_instances, desired_max_instances)` 后原子写 Run + Validation Allocation + pending create Job。最后一个 slot 上玩家与验证竞争时只能有一方成功。`reserved/create_unknown/creating/running/stopping/failed_unreclaimed/quarantined` 均占容量；仅可信 `released_no_effect` 或完整 `reclaimed` 释放。Node stale/offline 不释放。若 hard 下降导致已有占用高于上限，不改写历史，只禁止新增预留。

管理员显式 Validation 预留不要求该游戏/玩法已对玩家 `enabled` 或 `accepting_new_requests=true`，否则新 ArcadeGame 无法首次验收；它必须通过自己的 scoped gate、Controller 证明与总容量事务。验证 JoinInfo 仅在 Admin 受控详情中供 Owner 使用，不能因为验证实例 Ready 就出现在玩家节点选择或开放玩家 Join 控件。

## 6. ValidationRun 有限状态机

Run 的可持久状态为 `create_pending`、`create_observing`、`create_unknown`、`ready_no_join`、`awaiting_human`、`cleanup_required`、`stop_pending`、`reclaim_observing`、`stop_unknown`、`quarantined`、`passed`、`failed`。reserve 是创建事务内的逻辑事件：同一提交产生 `Allocation.reserved`、Run `create_pending` 和 create Job `pending`；不得提交一个没有 Job 的可领取 Run。`unknown` 由 `create_unknown`/`stop_unknown` 按阶段准确表达，均非终态。Ready 与 JoinInfo 是两个独立证据，不等于真人确认。

| 起点 → 终点 | 必需事实与动作 |
| --- | --- |
| reserve → `create_pending` | 第 5/7 节 gate 和容量成立；三条持久记录原子提交。 |
| `create_pending` → `create_observing` | Controller claim、解析可信模板、校验指纹与本机候选 ContentVersion/SHA、Platform 持久冻结 core key/path/port/指纹后才第一次调用 core；`accepted` 仅进入观察，不代表 Ready。 |
| `create_pending` → `failed` | 可信证明 core create 尚未发出，且本地模板/内容前置校验明确拒绝；create Job 终结为无副作用，Allocation 才可 `released_no_effect`。 |
| `create_observing` → `create_unknown` | create 调用/报告响应丢失或无可信结论；保留原 key、冻结请求、Node 和容量，按 FIX-05 对账。 |
| `create_observing`/`create_unknown` → `ready_no_join` | 同一可信 instance 的 core operation/status 证明 `active/running/ready`，但 JoinInfo 尚不可用或有结构化错误；禁止真人 PASS。 |
| `ready_no_join` → `awaiting_human` | Controller 对该 instance 实际端口提供有效 JoinInfo；Platform 核对当前 entry/network revision。若 Ready 与 JoinInfo 同时到达，可直接进入此状态，但两份证据均须持久。 |
| `awaiting_human` → `stop_pending` | 管理员确认 Owner 真人进服 `human_result=pass`，或确认失败 `human_result=fail`；在同一事务记录审计并为可信 instance 排入正式 stop Job。失败结果仍先回收。 |
| 任一 create 阶段 → `cleanup_required` | 启动失败/超时而已有可信 instance 或可能有副作用；有可信身份时排入/等待正式 stop；无可信身份时保持 unknown/隔离，不凭错误码释放。 |
| `stop_pending` → `reclaim_observing` / `stop_unknown` | stop accepted 后继续 operation/status；响应丢失时保留同一实例与容量，对账后收敛；不得把一个旧终态失败 operation 当成新 stop 成功。 |
| `reclaim_observing`/`stop_unknown`/`cleanup_required` → `passed` | 仅按下列全部 PASS 谓词；未知 stop Job 必须先收敛为终态。 |
| 上述需清理状态 → `failed` | create 明确无副作用且没有先前 unknown，或失败实例已完整回收；保存原因。真人失败、JoinInfo 不可用、旧模板不兼容即使已回收也为 failed。 |
| 有副作用歧义或身份/cleanup 无法可信收敛 → `quarantined` | 不 PASS，不释放容量，不自动另开 Run；可信晚到报告只可在资源真正收敛后进入 failed。 |

**PASS 谓词是合取：**Run 固定的候选 ContentVersion、VPK SHA256、TemplateRevision、绑定代次、内容/模板事实代次和 template fingerprint 与当前新鲜 Controller 事实一致；create Job 有可信 immutable instance/operation 身份，d2core 已 Ready；该身份曾有有效 JoinInfo；`human_result=pass` 且管理员已审计确认 Owner 真人进入；存在同一 Allocation/instance 的正式 stop NodeJob；stop 及对账已确认 `reclaimed/stopped/complete`；Allocation 为 `reclaimed`；create/stop 没有 unresolved `pending/claimed/accepted/unknown`；第 7 节 scoped gate 仍成立。PASS 时间由 Platform UTC 写入，PASS 历史不可撤回，但节点事实、绑定或维护代次漂移会使其不再是**当前可用准入证明**。

`human_result=pass` 后 stop 或 cleanup 失败，Run 保持 `stop_unknown`/`quarantined`，绝不 PASS。对于已发出的 unknown create，固定 core v0.1.1 没有安全 no-effect 证明；list 空、等待、重试拒绝、manager 重启均不能将其转成 `released_no_effect`。明确在首次 core 调用前发生的本地模板指纹不匹配可以拒绝并安全释放该次预留；若已可能发出 core 调用，漂移必须保留 unknown/占容，直到可信收敛。

## 7. Node × ArcadeGame scoped maintenance gate

`maintenance.begin(N,G)` 是日常内容/模板维护的正式起点：事务中关闭 `NodeContentBinding.accepting_new_allocations`，递增不可回退的 `maintenance_epoch`，审计操作者及原因。普通管理员仍可关闭绑定；Platform 只有在已开始且仍关闭的维护代次内才接受 ValidationRun 和 v1.0.2 内容发布。Content Tool 不接收这个令牌，运维须先确认 Platform gate 再手工 switch。关闭与调度必须在同一 Node/Binding 锁序串行化，不能由 UI 缓存证明。维护不自动 stop 已有实例或其它游戏。

创建 Run 前，Platform 在事务中重新读取并要求：

1. `(N,G)` 绑定存在、admission 已关闭、维护代次有效。N/G 的**旧** Allocation（两种 purpose）全部为 `reclaimed` 或合法 `released_no_effect`；相关 create/stop Job 无 `pending/claimed/accepted/unknown`。`quarantined`、`failed_unreclaimed` 和未回收 accepted 均阻塞。`integration_only` 或 core 中未入账且无法归属的现存实例同样使此 Node gate fail closed。
2. Node enabled、online（服务端心跳小于两分钟）、Controller/固定 d2core 兼容；Controller 声明第 12 节 capability；最近内容、模板和完整 inventory 事实新鲜且无 `unknown` 或未入账实例。
3. Content Tool 显式 switch 后，Controller 实际读回的 Workshop 内容版本与 SHA256 精确等于候选不可变 ContentVersion；模板绑定 key、generation 和实际 fingerprint 精确等于候选 TemplateRevision 在此 Node 的预期身份。template `unknown`、缺字段或不受支持依赖都不能视为匹配。
4. Node 总容量至少尚有一格；其它 ArcadeGame 的 Allocation **不参与 G 的旧资源排空判断**，但照常计入总 occupied。无需 `nodes.draining=true` 或整节点 occupied=0。

Run 已创建后，检查旧资源时排除**该 Run 自身**的 Allocation/Job，但其非终态资源持续占容量；PASS 时该 Run 也必须完整回收。维护期间可继续处理其它游戏的独立 Job。`reconcile/complete` 只表示做过一轮，不证明零未入账实例或零 unresolved Job。

发布和重新开放分别重新执行服务端核对：候选 PASS、目标绑定仍关闭、维护代次和指纹仍相同、Node/Controller/事实新鲜、未入账实例为零。发布可以发生在其它游戏占满剩余容量时；容量满只使新请求等待，不伪造可用 slot。不能通过一次 UI 刷新绕过上述条件。Content Tool 本身不接收维护令牌，也不判断平台资源；运维必须遵守此 gate 后才在节点运行 switch。

## 8. 模板机器身份与外部启动依赖

模板逻辑 ID `TemplateRevision` 属于 ArcadeGame；实际文件身份是**每 Node 的 NodeTemplateBinding**，因为固定模板含本机 executable、workingDirectory、cfg directory 等绝对路径，不能设一个跨 OS/Node 通用原始文件 SHA。绑定保存 `binding_key`、声明的 `expected_template_fingerprint_sha256`、递增 `binding_generation`；Admin 提交的是期望指纹和逻辑 key，不是任意节点文件路径。Controller 从本地配置解析 key 到 ASCII 绝对、版本化且不可原地改写的模板路径，并报告实际指纹。更改 key/预期指纹或受管依赖须递增 generation，旧 PASS 不再准入；t1 的启动语义变更必须创建 t2，不改写 t1 文件。

指纹算法版本 `template-manifest-sha256-v1`：对规范 UTF-8 清单计算 SHA256，清单包含已解析模板**绝对路径和文件原始字节 SHA256**，以及所有声明的、影响启动参数/cfg/readiness 的外部启动依赖的规范绝对路径、长度和 SHA256；条目按规范路径排序，长度前缀编码消除拼接歧义。模板 JSON 的 `arguments`、`cfg.lines`、`readiness` 已包含在模板文件字节中。d2core 每个实例在 `cfg.directory` 写出的临时 cfg 是输出文件，不作为静态依赖；该目录路径由模板字节覆盖，不能把其中其它可变 cfg 假装为不可变依赖。d2core 运行二进制/Dota 安装整体不纳入此内容维护指纹，它们仍按 Node 级维护。对于模板中的 `exec`、map/config 引用等无法由 Controller 安全穷举的外部启动依赖，节点本地版本化 manifest 必须显式列出递归依赖；静态依赖必须位于独立只读版本目录。缺失、不受支持、可变/链接目标身份不稳定时 `state=unknown` 并 fail closed。不能以只 hash JSON 文件声称覆盖任意外部 cfg；若某玩法无法使外部依赖可识别、不可变，它就不能获得本版准入证明。

Controller 在心跳/模板事实中报告 key、算法、状态、fingerprint 与事实时间；Platform 用服务端接收时间判断新鲜度，并仅在本轮最终模板事实的身份/状态改变时递增 `template_fact_revision`。Controller 本机配置为每个 binding key 指向版本化模板路径及其只读依赖清单；该清单须与模板放在受管版本目录中，不由 Admin Web 提供任意文件路径。Validation create Job 携 Platform 从 Run/绑定冻结的 `expectedTemplateFingerprintSha256`、绑定 generation、预期 Workshop ID/ContentVersion/VPK SHA；Controller 以 Workshop ID 定位本机 ContentBinding，在 prepare 前核对本地 manifest 和候选内容事实，并把实际 fingerprint 随 prepare 写入 immutable `node_job_executions`。Platform 比较 expected/observed 后才确认冻结执行；Controller 在第一次 core 调用前再次校验模板文件和本机内容身份。重试必须使用同一 Job/key/path/port/fingerprint，且本地文件/内容仍匹配；若已可能发出 create 后发生身份漂移，不猜测为无副作用，而是继续对账既有 operation/instance，保持占容，无法收敛时隔离。core 自身的 create 请求指纹仍按固定 v0.1.1 的 key/path/port 语义，不伪称新增字段进入 core 协议。文件在最后校验与 core 打开之间仍需节点运行账户的不可变版本目录/权限纪律；不得把可写模板路径视为已由 SHA 自动消除竞态。

## 9. 未入账实例与 inventory 事实

Controller 成功 `d2core list` 后，向 Platform 的新增 **v1 additive inventory report** 发送本 Node 所有尚不能确认 `reclaimed/stopped/complete` 的 core instance 的 `instanceId/lifecycle/process/cleanup` 与完整扫描标志；空数组只有在 list 成功且结果确实为空时才是零实例事实。list 失败、缺字段、截断、重复身份、旧事实或 Controller 尚未核对，状态为 `unknown`，不能按空集处理。Platform 使用已认证 Node 身份和服务端收到时间，按自己的 `node_jobs`、`allocations` 及不可变 create instance 身份比对；只有同 Node、关联正式非资源终态 Allocation 的可信身份才算已入账。`integration_only` 实例、终态 Allocation 对应的活跃实例、没有可信 Job 归属的实例，都计为 `unaccounted`。

`POST /inventory` 请求的最小结构为 `{scanId, complete, instances:[{instanceId,lifecycle,process,cleanup,currentOperationId}]}`；`scanId` 是 Controller 本次 list 尝试的唯一随机/单调不重复标识，`complete=true` 仅在一次 list 全量解码成功且未截断时有效。Platform 按 `scanId` 去重，并在 Node 锁下将这份原子快照、服务端接收时间、已入账/未入账 ID 摘要持久化。list 失败时 Controller 必须发送 `{scanId,complete:false,instances:[],errorCode}`；若此报告因网络故障不能送达，下一次心跳的 `inventoryState=unknown` 或缺失匹配的 `inventoryScanId` 会使旧快照不可用于新 gate。Node API 不接收 Platform 预先猜测的游戏归属。

inventory 报告必须与一次成功的本地 list 和本轮 open Job/active Allocation 对账关联；Admin 可见“完整/未知、未入账数量、最近时间及可审计身份摘要”，不开放自动 stop。`unaccounted > 0` 使该 Node 的内容维护/ValidationRun/发布节点证明 fail closed；即使不能判断它属于 Game A 还是 B，也不得猜测归属。该条件针对**未入账**实例，不把其它游戏已入账的活动 Allocation 当作 Game B 的排空障碍。运维通过既有受控诊断收敛；不自动接管、改派、kill 或停止未知实例。与任何外部系统一样，无法防止获授权操作员绕过平台在报告后手工直接 create；v1.0.2 正式内容验收禁止这条旧常规路径，运维应保持节点访问纪律。

## 10. 受控未来模板指针与发布记录

本版采用现有 `GamePreset.template_revision_id` 作为**未来 Allocation** 指针，不建立完整 GamePreset revision 系统。新增受控 `release.publish`；普通 `preset.update` 只管理 enabled/accepting/message，不能切换 TemplateRevision。发布记录是小型不可变成功记录：`release_id`、Game、old/new ContentVersion、每个受影响 Preset 的 old/new TemplateRevision、旧/新 accepting 状态、引用的各玩法 PASS Run ID、验证 Node 和准入策略、`published_by`、Platform UTC 时间、可空 `rollback_of_release_id`；AuditEvent 同事务记录这些 ID 与前后指针。候选尚未发布时只存在登记的版本/模板和 Run，不创建通用 release pipeline。

`release.publish` 请求包含 `expectedOldContentVersionId`、每个目标 Preset 的 `expectedOldTemplateRevisionId`、目标新值、拟保持/暂停/开放的玩法集合和引用 Run ID；服务端不相信 Admin 页面缓存。**某游戏首次进入 v1.0.2 发布合同（包括仅模板更新）时，必须列出该游戏全部现存 Preset**：同一事务将它们全标为 `v1_0_2`，无当前 Node/组合证明的玩法置 `accepting_new_requests=false`。此后可只列本次受影响玩法逐个发布，但每个开放的玩法仍需自身证明。内容指针从 v1 改 v2 时，即使全部玩法已经是 `v1_0_2`，也必须重新列出全部 Preset，以免保留 t1 指针的玩法在新 v2 下漏入调度。已验证玩法可以发布和开放；不要求全玩法同日完成。引用 PASS 的节点除目标 binding 在发布前必须关闭外，还须 `enabled`、全局接受请求、非整节点 Drain、Controller 兼容、事实新鲜并无未入账实例；容量暂满只会使发布后请求等待。

事务按第 15 节锁序：CAS 核对正式旧指针和旧 accepting 值；校验 ContentVersion/TemplateRevision 均属于该 Game、每个欲开放玩法有当前 Node/维护代次上的 PASS 且该 Node 事实仍匹配、没有未入账实例；插入 release 主记录及逐玩法差异/证明；原子更新游戏内容指针和目标玩法模板指针、将未验证玩法暂停，并在该游戏首次 v1.0.2 发布时将全部玩法的 `validation_contract` 提升为 `v1_0_2`；写 Audit；一次提交。冲突返回 409 且不写成功记录。发布不自动打开 NodeContentBinding；waiting Request 在之后真正预留时读取新正式指针。新增游戏首个发布也走同一动作，以期望旧内容为空值作 CAS。

`binding.update accepting=true` 是**单独的**节点准入动作，必须复查服务端当前指针/事实/维护代次/Run 证明；允许某 Node 只具备 P1 证明而 P2 仍暂停。对 `validation_contract=v1_0_2` 的玩法，即使绑定被打开，调度 SQL 仍必须逐 Node/玩法/组合检查有效 PASS。`preset.update accepting=true` 也必须至少有一个可验证的目标 Node/正式组合证明，否则拒绝，防止 UI 宣称可开放而所有节点均无证据。证明失效时调度自动 fail closed，已有 Allocation 不被改写或自动停止。

**旧内容动作边界：**只有该游戏所有现存 Preset 仍为 `legacy_v1`、且从未完成 v1.0.2 release 时，才可为滚动升级保留原 `content.validate` / `content.publish` 路径。一旦该游戏任一玩法为 `v1_0_2`（包括新建玩法），或该游戏已完成首次 v1.0.2 release，两个旧动作对该游戏均须拒绝：`content.validate` 不得创建/更新可用于新准入的证明，`content.publish` 不得修改正式 ContentVersion 指针。此后所有 ContentVersion / TemplateRevision 正式切换只走 `release.publish`；不能通过把玩法重新标为 legacy 恢复旧路径。旧 `content_release_validations` 仅保留历史和仍合格的 legacy 路径含义，永不转换成 ValidationRun PASS。

## 11. 标准运维流程

### VPK-only

登记候选 ContentVersion/SHA → 目标 Node × Game `maintenance.begin` → 旧目标图资源完全回收 → 运维以已有 Content Tool 执行 `prepare/switch/status` → Controller 精确报告新版本和 SHA → 先以现有 t1 逐玩法运行 Platform ValidationRun → 真人验证/正式 stop/full reclaim/PASS → `release.publish` 更新内容指针并暂停未覆盖玩法 → 分别复查并打开可用 Node binding、已验证玩法。若 `(v2,t1)` 失败，仅在日志和启动事实表明模板语义变化后登记 t2，创建新 Run 验证 `(v2,t2)`；不能降低 readiness 要求。

### Template-only

VPK 和 SHA 不变，无 Content Tool switch。登记 t2，在 Node 本地准备独立、版本化模板与外部依赖，登记期望指纹；关闭目标图新分配，让该图旧实例按 t1 快照自然结束并完整回收；验证 `(v1,t2)`；PASS 后 `release.publish` 只改变对应 Preset 的未来模板指针。旧 Allocation 的 t1 快照与其 core 实例独立保留直到正常回收。该游戏首次 v1.0.2 发布时，未验证的其它 Preset 即使保留 t1，也暂停；它们取得各自 `(v1,t1)` 证明后可逐个开放。

### Combined / 新图

联合更新先测试 `(v2,t1)`，证据证明需要时再创建 t2，验证 `(v2,t2)`，原子发布目标指针。新图创建未启用 Game、首个 ContentVersion、每个所需 TemplateRevision/GamePreset/Node binding，使用**同一个** ValidationRun 生命周期逐玩法验收，通过后初次发布，再开放该图/玩法及 Node binding；最后以普通 Player Web 完成额外真实开服与回收验收。不另造新地图验证实例类型。

## 12. Node API v1 / Controller 兼容合同

本设计核对现有 `nodev1.Job`、Heartbeat、`/jobs/{id}/prepare` 与 `runner.Step`：它们可承载同一个 create/stop Job 生命周期，但没有模板字节身份或 core 完整 inventory 事实。**本节和第 13 节的 execution-fence 合同以 [Owner execution-fence amendment](v1.0.2-execution-fence-amendment.md) 为准：逐请求 Platform 授权、持久 operation-start、已授权 in-flight effect 是不同边界。**Node API 路径与 `APIVersion=1`、固定 d2core local protocolVersion=1 保持不变；operation-start 是 wire-additive 路由。旧 Controller 对未知响应字段可忽略，旧请求缺新字段仍可用于既有玩家组合；Platform 不得把这些缺失值当作 v1.0.2 验收事实。

| v1 增量 | 合同 |
| --- | --- |
| Heartbeat `capabilities` / inventory 状态 | 字符串集合，明确包含 `contentValidationV102`、`templateManifestSha256V1`、`coreInventoryV1` 才能参与新验收；空/缺失=不支持。心跳带最新本地 list 尝试的 `inventoryScanId`、`inventoryState=confirmed/unknown`；Platform 只有在对应成功完整 inventory report 已持久化且 scanId 相同时才接受“零未入账”。Platform 仍按既有版本/commit/protocol 检查 d2core 兼容。 |
| Heartbeat `templateFacts[]` | 按本机 `bindingKey` 上报 `state=confirmed/unknown`、算法版本与 fingerprint；缺失和旧心跳不可作 PASS。Platform 与 NodeTemplateBinding 的期望值/代次比对，保存 Controller-reported fact，不允许 Admin 填报该事实。 |
| `POST /inventory` | 认证的 Node 提交第 9 节完整 list 事实，响应含 Platform 收到时刻、未入账计数/状态；失败报告不覆盖旧事实为“零”。大小、去重和合法状态受限。 |
| create Job 的可选 `expectedTemplateFingerprintSha256`/binding generation/`expectedWorkshopId`/`expectedContentVersionId`/`expectedVpkSha256` | 用于 v1.0.2 Validation 和采用新准入的普通 Allocation；老 Job 无字段仍用旧执行合同。Controller 未声明 capability 不得领取/执行需新身份合同的 Job。首次 core create 前 Controller 须由 Workshop ID 定位本机内容绑定并读回版本与 SHA；缺失/不符时在尚未调用 core 的前提下结构化无副作用拒绝。 |
| `/jobs/{id}/prepare` 的可选 observed fingerprint/manifest algorithm | Platform 在首次 core 调用前比较 expected/observed，随 key/path/port 持久冻结；重复 prepare 必须相同。未发 core 前的确定 mismatch 可结构化无副作用拒绝，已可能发出后只能 unknown/对账。 |

**执行能力 fence（依 Owner amendment 收窄）：**任何要求 v1.0.2 新机器身份证明的 create/stop Job（包括 ValidationRun Job、采用新准入的玩家 Job）在持久创建时标记不可降级的 required capability；其已 prepare 的 frozen execution 和后续恢复仍继承此标记。Node 共享凭据或该 Node 上一次 heartbeat capability 不能代表当前 HTTP 调用者。Platform 必须对**本次请求所属的 Controller 进程/会话**取得经认证、仍有效且涵盖 Job 所需能力的证明，逐次在 `/jobs/open`、claim（含 independent-stop）、GET job、prepare、恢复读取、report、operation-start，以及可触发执行/状态收敛的 active-allocation、instance-fact 与 inventory 路径核验。无证明/过期/能力不足时，读列表必须过滤这些 Job/Allocation 和 frozen payload，按 ID 读取或写入必须拒绝；不能先返回敏感 Job 再期望旧 binary 自行跳过，也不能只在 claim 或 prepare 检查一次。相同 Node 凭据下旧正式进程不得自动继承新进程的能力会话。任何本地 v1.0.2 `Core.Create/Stop` 前，当前 session 必须先将该精确 Job/冻结身份持久提交为 `unknown` / MAY-HAVE-STARTED；提交后 session 变化不追溯撤销该次 in-flight operation，也不能据此推断无副作用或释放容量。该 HTTP fence 不覆盖之后的本地 core 调用；普通 heartbeat 字段不提供请求授权。

Platform 为旧 Controller 保留**现有 v1.0.1 普通业务组合**的兼容过渡：旧进程仍能取得、恢复、执行和报告 legacy Job，但看不到、拿不到、恢复不了、执行不了要求 v1.0.2 capability 的 Job。现有 Node HTTP 请求解码严格拒绝未知字段，所以升级顺序必须先部署认识新增请求字段的 Platform，再部署新 Controller；新 Platform 对旧 Controller 仍发送旧请求形状，并在服务端对 legacy/new Job 分流。若无法在 Node API v1 的真正 additive wire 合同下证明上述逐请求隔离，实施前**必须明确升级 Node API 协议版本并设计兼容迁移**，不得宣称 heartbeat capability 已解决该问题。Controller 新 binary 继续调用固定 d2core 正式本地 Go client，不执行 Content Tool、任意 CLI、Shell 或文件浏览 Web 命令。

## 13. Controller 与 Job 恢复约束

Controller 启动/重连仍按 `core.List → open NodeJob/frozen execution → operation/status → active Allocation fact → 新 claim` 恢复，但每个 Platform Job/Allocation 读取和后续报告均受第 12 节本次请求能力 fence 约束。新版正式 Controller 在取得 capability session 之前须持有整段进程生命周期的 Node-local OS exclusive lock。旧 Controller 在此流程中只见 legacy 工作；即使新 Controller 已 prepare/freeze 一个 v1.0.2 Job 后崩溃或被旧 binary 替换，旧进程也不能取得其 frozen request、发起**新的** v1.0.2 operation-start 或报告状态。先前已经持久 operation-start 的旧新版进程可能随后完成该精确本地 core call；Platform 在此之前已经保留 unknown/占容。新有能力的进程沿**同一 NodeJob、同一 idempotencyKey、同一冻结 path/port/指纹**或同一 formal stop Job/instance 恢复；即使崩溃发生于 marker 与实际 core call 之间，也不得按 no-effect 释放。验证 Job 和普通 Job 在同一 claim 冲突谓词下：同 Allocation/instance 不并行，独立 Allocation 的 Job 可推进。NodeJob ID 唯一决定 core idempotencyKey；不能因为 Controller 重启、绑定改变或第一次响应丢失而生成新 key。`PrepareCreate` 的 path、port、key、模板指纹已冻结后，重试只接受完全一致的值。模板文件漂移不导致改用新路径/文件：Controller fail closed，Platform 保留资源与原 Job，直到可信 reconcile/stop 或隔离。核心 operation 的 accepted 不是 Ready，完整回收仍靠 status 三元条件。

## 14. 多节点滚动与 rollback

初始 A/B 均为 v1+t1。A 只关闭 Game G，A 上 Game X 等其它游戏照常运行；G 的旧 Allocation 回收后切 A 的 VPK，逐玩法 PASS 并发布 P1 的 v2+t2，P2 未覆盖则暂停。A 取得当前证据后开放 P1。B 报告 v1 或旧模板事实时不能接 v2+t2 新 Allocation；B 的旧 G 实例继续运行直至自然结束，再单独 scoped 维护、switch、PASS 并加入新版池。A/B 无需同时整 Node Drain。

发布后的 rollback 是另一次 `release.publish`，`rollback_of_release_id` 指向被回退发布。先在至少一台可用 Node 恢复旧 ContentVersion 的真实文件/链接，Controller 报告旧 SHA、旧 TemplateRevision 的当前模板指纹，按**本次维护代次**取得旧组合逐玩法 ValidationRun PASS；再原子把正式内容/相关玩法模板指针切回，未获旧组合证明的玩法暂停，最后逐 Node 复查开放。保留新旧 release 和 Allocation 历史。单纯改数据库指针、假定旧 VPK 已回到磁盘或复用失效旧 PASS 均不构成 rollback。

## 15. 并发、锁顺序与原子性

现有调度实际顺序是：先 waiting ServerRequest 锁，再全局/Game/Preset 共享锁，后 Node 排序独占锁；`content.publish` 已先锁 Game。现有 `request.stop` 是 ServerRequest→Allocation，而 `ReportJob` / `ReportInstanceFact` 在 Job/Allocation 后更新 ServerRequest；该反向顺序必须在实施时**整体修复**，不能保留“报告路径局部 Job→Allocation”的旧说法。本版冻结同时适用于玩家调度、Admin stop、Job 报告/对账、发布和节点事实的统一行锁顺序；不参与的对象可跳过，但不得逆序取得：

```text
ServerRequest（所有 player-owned 路径，包括报告、对账与 stop）
→ PlatformSettings（若参与）
→ ArcadeGame
→ GamePreset（按 ID 升序）
→ Node（按 ID 升序）
→ NodeContentBinding（按 Node ID、Game ID 升序）
→ NodeTemplateBinding（按 Node ID、TemplateRevision ID 升序）
→ NodeJob（同一事务多行按 ID 升序）
→ Allocation（同一事务多行按 ID 升序）
→ NextGameIntent（若参与）
```

对 player-owned Allocation，凡同一事务读取并可能修改 ServerRequest、NodeJob、Allocation 的路径，一律先锁 **ServerRequest→相关 NodeJob→Allocation**；若还需上表公共对象，仍插在 Job 之前的对应位置。对没有 ServerRequest 的 Validation Allocation，锁相关 **NodeJob→Allocation**。`ReportJob`、`ReportInstanceFact`、`request.stop`、next-game stop、Admin stop/terminate/quarantine、自动 stop、quarantine/reclaim 的所有状态转换都遵守这一顺序；`ReportInstanceFact` 即使只需核对 create Job 身份，也须在 Allocation 前锁该 Job。允许先用无锁查询找到关联 Request/Job/Allocation ID，然后按正式顺序取得行锁，并**重新核对 owner、Job/Allocation/instance 关联及当前状态**；无锁查询不是状态决策。不得持有 Job/Allocation 后才更新或锁旧 ServerRequest，也不得在锁 Allocation 后反向等待相关 Job。ValidationRun 的 stop/report/reconcile 走无 Request 分支。

状态推进、stop Job 建立与必要的 Request/Allocation 更新保持同一事务；既有 create 身份、固定 key、unknown/隔离和完整回收才释放容量的条件不变。同一 Allocation/instance 的 open stop 唯一约束和锁内状态复查共同保证幂等，竞争时不能重复排入 stop 或丢失 quarantine/reclaim 终态。NextGameIntent 的消费/暂停位于同一顺序末端，不得反向取得源 Request。NodeJob claim 当前先锁 Node 后锁 Job，若未来要在 claim 事务修改玩家 Request，也必须改走上述顺序，不能 Node→Request。维护/发布 gate 在公共锁内只读取资源的**单调终态**，不得再持有 Allocation 行锁反向等待 Node/Binding。Controller 心跳只更新 Node→Binding/模板事实，不反向锁 Game；它与 publish/Validation 在 Node 锁处串行。`binding.update` 和 `template_binding.upsert` 必须先取得 Node 锁再改绑定；当前只锁 Binding 的实现需要在 Implementation Phase 修改。调度在 Node 锁后对目标 Binding/TemplateBinding 取得共享锁并**再次**核对准入、模板、内容和容量，不能只读无锁快照。发布先锁 Game/全部相关 Preset，再锁证据 Node 与绑定，CAS 更新指针；新 Allocation 对正式组合的共享锁使发布前后快照各自完整，不产生 v2+t1 之类非计划的交叉读值。

最后一个 slot 的玩家调度与 Validation reserve 均用同一 Node 行独占锁和同一个 `occupied` SQL；关闭绑定与预留要么预留先提交、随后 gate 等待它完整回收，要么关闭先提交、调度发现 closed 而不预留。heartbeat/模板事实在 Node 锁下序列化后，publish/Run PASS 只使用事务内重新读取的事实；UI 显示不是事务输入。可在实现时选择等价 advisory/row-lock 组合，但必须保持这些外部可观察次序与测试。

## 16. Schema migration 草案（仅合同，不是 SQL 实现）

从 migration 19 之后新增前向 migration；旧 migration 文件与 checksum 不变：

1. `validation_runs` 主表：第 4 节身份、不可变候选快照、状态/结果/失败码、管理员确认、关键时间；FK 保证 GamePreset/ContentVersion/TemplateRevision 均属同一 ArcadeGame；唯一 Run ID。禁止删除或改写候选身份。
2. `allocations` 加 `purpose`、可空 `validation_run_id`，`server_request_id` 允许仅 validation 行为空；CHECK owner XOR、唯一 ValidationRun FK、验证 attempt 序号约束；扩展 identity trigger；旧行全回填 player，原玩家唯一索引与容量状态不变。
3. `node_template_bindings` 加期望 manifest 指纹与 `binding_generation`；新增 Controller-reported template fact 表，保存状态/指纹/服务端时间/`template_fact_revision`，与管理员期望严格分开。`node_content_bindings` 加 `maintenance_epoch` 和 `content_fact_revision`。两种事实 revision 仅在 Controller 实测身份/状态改变时递增，重复相同心跳只刷新接收时间；维护 epoch 仅随 `maintenance.begin` 递增。现有心跳会先把全部内容绑定置 `unknown` 再逐条 upsert，实施时必须改为在同一事务比较**上一轮最终事实与本轮最终事实**，不能让这个临时重置使 revision 每次心跳都递增。模板绑定 generation 仅随 key/期望指纹/依赖身份变动递增。各代次均单调；无值不回填为“已确认”。
4. 新 Node inventory 快照/异常摘要表；完整上报由 Platform 与已有 Allocation/Job 对账后计算未入账。旧 Node 缺事实默认为 unknown。
5. `node_jobs` 加不可降级的 required capability 标记，并使 `node_job_executions` 的冻结记录继承该要求；另加可空冻结模板 manifest 指纹/算法。旧 Job 维持 legacy 要求。NodeJob 现有 `integration_only=(allocation_id IS NULL)` 约束不放宽，现有 create/open stop 唯一索引可继续使用；frozen Job 的权限不能只靠当前 heartbeat 推导。
6. `content_releases` 与逐玩法 `content_release_presets`/引用 Run 的表：成功发布的 old/new 值、证据、操作者、rollback 关联；不可改写历史。`game_presets.validation_contract` 枚举 `legacy_v1|v1_0_2`；现有行迁移为 legacy，新建玩法为 v1_0_2。游戏首次 v1.0.2 发布（含 Template-only）使该游戏全部玩法进入 v1_0_2，未验证者同时暂停；以后内容指针升级也使全部玩法按新组合重验。标记不可降回 legacy。
7. `content_release_validations` 保留历史/受限 legacy 意义，不能回填为 ValidationRun PASS。`content.validate` / `content.publish` 必须按第 10 节对已进入 v1.0.2 合同的游戏设数据库事务内 guard，不能因旧表存在而写入新证明或改正式内容指针。首次 v1.0.2 发布与 rollback 要求真实新 Run；现有 v1.0.1 正式组合在仍合格的 legacy 游戏上继续按旧业务方式运行。

具体 SQL 约束名、索引和迁移拆分属于 Implementation Phase，但不能改变本节 owner XOR、唯一关系、历史不可变及旧数据保留语义。新 Platform binary 与 migration 必须配对；数据库前向迁移不会随 binary 回滚自动撤销。回滚应用前须核查旧 binary 是否能读新 schema 与未终结 ValidationRun，不能用恢复备份掩盖真实 d2core 资源。

## 17. Admin API 草案（仅合同，不是现有端点）

现有同源、独立 AdminSession、CSRF/Origin、严格 JSON 未知字段拒绝、事务审计继续。新增动作可仍走 `POST /api/v1/admin/actions`；详情可用 `GET /overview` 的脱敏 Run/release 摘要及分页详情，避免最近 100 条截断使关键 Run 不可追溯。

| 动作 | 必需输入及语义 |
| --- | --- |
| `maintenance.begin` | `nodeId, gameId, expectedBindingState/epoch`；关闭目标 binding、递增 epoch、审计；若 Node/Game 不存在或状态已变化返回 409。重复请求用客户端 request ID 或当前 epoch 精确幂等，不凭重复点击多次递增。 |
| `template_binding.upsert` 扩展 | `nodeId, templateRevisionId, bindingKey, expectedTemplateFingerprintSha256, expectedOldBindingGeneration`；在 Node→Binding 锁下 CAS，变更身份才递增 generation，缺失期望指纹不得用于 v1.0.2 Run/准入；只配置 t2 的版本化本机文件，不把现存 t1 原地改写。 |
| `validation.start` | `nodeId, gameId, presetId, contentVersionId, templateRevisionId, expectedMaintenanceEpoch, expectedTemplateFingerprint, requestId`；服务器复核全部 gate/容量，原子 Run+Allocation+create Job，重复 requestId 返回原 Run，不能重复开房。 |
| `validation.confirm` | `runId, result=pass|fail, confirmed=true, expectedRunState`；保存管理员对 Owner 真人实测的声明，并在可信 instance 身份下原子排入正式 stop。`pass` 只表示 human_result，不返回“最终 PASS”。无 Ready/JoinInfo 不可 pass。 |
| `validation.stop` | 对已知可信实例请求清理，包括已失败/无 JoinInfo 的 Run；不能传任意 instance ID，不能绕过同 Allocation open Job 冲突。unknown 且无 ID 时只允许隔离/对账。 |
| `release.publish` | 第 10 节 expected-old CAS、全部受影响 Preset 的计划、引用 PASS Run、可选 `rollbackOfReleaseId`；成功才产生 release record/Audit。首次内容发布允许 expected old 为空。 |
| legacy `content.validate` / `content.publish` | 仅对第 10 节仍符合 `legacy_v1` 条件的旧游戏保留；服务端在各动作事务内重查该游戏所有 Preset 合同及 release 历史，不满足即拒绝。旧验证记录不构成新 PASS，旧 publish 不能触碰升级后的正式指针。 |
| `binding.update accepting=true` / `preset.update accepting=true` | 保留动作名但新增 v1.0.2 证明 gate；拒绝旧 Controller、缺失/失效组合证明。普通 `preset.update` 不接受模板字段。 |

客户端 request ID 是管理员动作防重复键，不取代 NodeJob 固定 key；服务端必须将相同 request ID 的不同 payload 拒绝。失败返回 409/明确错误码（如 `SCOPED_RESOURCES_ACTIVE`、`CAPACITY_FULL`、`CONTENT_FACT_MISMATCH`、`TEMPLATE_FACT_MISMATCH`、`INVENTORY_UNKNOWN`、`UNACCOUNTED_INSTANCE`、`VALIDATION_INCOMPLETE`、`CAS_CONFLICT`），不得写成功审计或伪造 Node fact。Admin 只提交逻辑 ID/期望指纹，不得提交本机路径、Shell 命令或任意 core 参数。

## 18. Admin UI 合同

内容页显示每个游戏的正式 content、每个玩法正式 template 与候选 `(content,template)`，并以 Node × Preset 显示：目标绑定是否关闭、旧资源是否回收、Controller 内容 SHA、模板指纹、inventory/未入账、剩余容量、Run 的 create/Ready/JoinInfo/真人确认/stop/reclaim/PASS 状态、当前证明有效或失效的具体原因。P1 PASS/P2 缺证明时应明确显示“P1 可开放，P2 保持暂停”，不得仅显示游戏级“已验收”。

按钮由服务端状态驱动：开始 scoped 维护、创建 Run、确认真人通过/失败、请求正式 stop、发布单个或多个已验证玩法、打开对应 Node binding/玩法；每次动作仍以服务端重验为准。新流程移除“整 Node Drain、occupied=0、人工直接 d2core create”的日常提示和浏览器内逐玩法勾选作为验收凭据。维护说明仍指出 Content Tool 与模板文件须在节点本地由运维准备；Admin 不上传文件或远程执行命令。旧 Admin content/node workflow 在功能实现阶段更新，当前 UI 不能用于执行本规格。

## 19. 失败与安全回退矩阵

| 情况 | 冻结处理 |
| --- | --- |
| v2 VPK 内容异常、尚未发布 | 候选不发布；目标 binding 关闭。所有验证实例完整回收后显式 Content Tool rollback，Controller 再读回旧版本/SHA，旧组合重新取得当前维护代次 PASS 后开放；正式指针未变化，无需制造一次“回退” release，只记录候选放弃与操作审计。若 v2 已发布，改走第 14 节受控 rollback release。 |
| v2 正常、t1 readiness 不兼容 | 保存 `(v2,t1)` 失败 Run 和日志诊断；保留 v2 候选，登记版本化 t2，创建新 Run 试 `(v2,t2)`。不删除安全 marker 充数。 |
| t2 仍不 Ready或真人失败 | 旧正式指针不动，候选不发布；已产生实例先 stop/full reclaim，失败记录保留。 |
| create response unknown | 同一 Job/key/冻结参数对账；容量保留，不创建第二 Run、不换 Node；FIX-05 禁止 unknown 后 no-effect 释放。 |
| Validation instance quarantine | 不 PASS、不开放、不发布、不释放占用；可信身份恢复后沿原实例收敛。 |
| Controller 重启 | durable Job/Allocation/Run 与 core list/operation/status 恢复；模板漂移 fail closed，不重复 create。 |
| 事实漂移或未入账实例 | 当前准入失效；已在运行的玩家 Allocation 保留原快照与资源，停止新分配；运维核对后新 Run/重新开放。 |
| 发布后的 rollback | 第 14 节作为新 release；禁止只改 DB 指针或假定 Content Tool 文件状态。 |

## 20. 测试合同与交付门槛

功能实现阶段必须有下列证据；本规格阶段不创建测试代码或真实实例。

| 层级 | 必过项 |
| --- | --- |
| Unit | 候选 `(v2,t1)` 与 `(v2,t2)`、模板 CAS、逐 Preset 覆盖、scoped gate 排除 Game A 但计其容量、PASS 全部前置条件、unknown/quarantine 永不 PASS、旧证据因 epoch/指纹漂移失效。 |
| PostgreSQL | 最后 slot 玩家 vs Validation 只能一方 reserve；binding close vs scheduler 两种串行顺序；publish vs heartbeat/template binding 变更；Game/Preset CAS 与 Allocation 快照；旧 Allocation 身份 trigger。强制并发交错 `request.stop` vs `ReportJob` / `ReportInstanceFact` 的 quarantine、reclaim、stop-related 转换，并覆盖 next-game/Admin stop：证明无 deadlock、无重复 stop、无丢失终态、无不安全容量释放。 |
| Failure injection | create 响应丢失、accepted 后 Controller 断联、stop 响应丢失、晚到报告、failed_with_effect 与完整回收、unknown 禁止 no-effect、FIX-05 保持、模板校验前后漂移。 |
| Controller recovery | **必过混版序列**：有能力的新 Controller prepare/freeze v1.0.2 create（另覆盖 stop）→ 崩溃/停止 → 同 Node 凭据的旧 Controller 启动，对 `/jobs/open`、claim、GET job、prepare、active-allocation、report/instance-fact 均不能取得或推进该 Job/Allocation，也不能 core create/stop → 有能力的 Controller 返回，仍以同一 Job、idempotencyKey、冻结请求/模板指纹恢复，无重复实例。另验 capability 会话过期/丢失时保持 unknown 与容量；core history 过期 fail closed；inventory list 失败/截断/未入账保持 unknown 或阻塞。 |
| API/Web | 逐请求 capability fence 覆盖 pending、claimed、accepted、unknown 与已 frozen 的新 Job；旧 Controller 仍能处理 legacy Job；缺能力的旧请求不会因该 Node 上一次新 heartbeat 得权。Admin 严格字段、越权与重复请求；P1 PASS/P2 暂停；旧 `content.validate`/`content.publish` 对升级游戏拒绝、对合格 legacy 游戏保留；UI 展示证据缺口且服务器拒绝过期页面动作。 |
| Real-node | Windows/Linux 隔离环境验证正确模板指纹/外部依赖、真实 Ready/JoinInfo、真人进入、正式 stop/full reclaim；同 Node 双游戏并行与 Node A/B rolling。Production 需另行显式授权。 |

最终 Production 验收场景：Node A 的 Game A 有真实玩家活动实例并记录原 instance identity。关闭 Node A × Game B admission，等 B 旧 Allocation 完整回收，切换 B 候选 VPK 与版本化模板，Controller 读回精确内容/模板事实且 inventory 无未入账实例。Validation Allocation 正式占一格，沿 NodeJob/core 达到 Ready、有效 JoinInfo，Owner 真人进入 Game B；正式 stop/full reclaim 后 Run PASS，发布 B 新组合并开放，新的 B Allocation 快照新 content/template。**Game A 的真人客户端全程不断线，instance identity 不变化，最终仍按原生命周期回收。**数据库状态与 d2core 理论多实例能力不能代替真实客户端证据。验证失败、rollback 和 B 节点后续滚动均留 Audit/Run/release 关联。

## 21. 实施范围与阶段拆分

推荐按依赖顺序授权后续实现，不在本规格会话执行：

1. **Schema + Store 安全账本**：Migration、Run/purpose、容量与 gate/锁、状态分流及 PostgreSQL 竞态测试。
2. **Controller / Node API v1 additive 证明**：模板 manifest/prepare 与 inventory/capability，双平台恢复测试；不改固定 core/Content Tool。
3. **发布和 Admin 合同实现**：逐玩法 `release.publish`/rollback、Node 准入、Admin API/UI 与文档更新。
4. **隔离真实节点验收**：完整人测、失败注入、跨游戏/多 Node 滚动；Production 验收、部署、Tag/Release 分别授权。

本文件冻结设计和接受条件，不构成实现、migration 执行、Production 连接或部署授权。
