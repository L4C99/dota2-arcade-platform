# 1. 项目背景与目标

当前已有面向玩家的临时服务方式，以固定公共服务器为主。

实际问题：

- 玩家可能撞车；
- 房间归属不清；
- 多人可能误操作；
- 无法按申请安全独占资源；
- 多节点以后难以统一调度；
- 运维需要人工判断实例是否真的已经回收。

V1 的第一目标不是建设完整匹配平台，而是：

> **让玩家通过网页自助申请一个归属于自己或当前队伍的 Dota 2 游廊专服；实例就绪后优先提供一键进房；游玩结束后由平台安全停止并回收底层资源。**

预计规模：

- 每日玩家总数约不超过 100；
- 同时网页操作通常低于约 20；
- 初期 1–2 个游戏节点；
- 玩家主要是群友/熟人；
- 单人申请最常见；
- 偶尔多人固定组队；
- 游戏节点资源是主要瓶颈，Web 控制面不是。

V1 优先级：

1. 状态正确；
2. 不重复开房；
3. 不误释放资源；
4. 重启/断线后可恢复；
5. 运维简单；
6. 尽快形成可长期运行的完整初版。

# 3. 关键术语速查

本节是整份任务书的统一词典。

## 3.1 用户与队伍

| 中文称呼 | 代码名 | 含义 |
|---|---|---|
| 用户 | `User` | 平台里的一个人。V1 使用匿名身份，未来可绑定 Steam |
| 登录会话 | `Session` | 浏览器证明“我是这个 User”的凭证；Session 不是 User 本身 |
| 队伍 | `Party` | 长期存在的一组玩家，不随某一局服务器结束而消失 |
| 队伍成员 | `PartyMember` | 用户与队伍之间的成员关系，包含队长/队员身份 |
| 邀请链接 | `PartyInvite` | 加入某个队伍的高熵邀请凭证 |

## 3.2 游戏内容

| 中文称呼 | 代码名 | 含义 |
|---|---|---|
| 游廊游戏 | `ArcadeGame` | 一份游廊/Workshop 内容，通常对应一个 Workshop ID |
| 玩法预设 | `GamePreset` | 同一游廊游戏下玩家可选的玩法、难度或服务器配置，例如 N6、N7、Solo |
| 内容版本 | `ContentVersion` | 某一版实际服务端内容/VPK。Workshop ID 可以不变，但 VPK 文件内容可以变化 |
| 模板修订版 | `TemplateRevision` | 某一版 d2core 启动模板，包括启动参数、cfg、Ready 规则等 |
| 节点模板映射 | `NodeTemplateBinding` | 把一个逻辑 TemplateRevision 映射到某台节点上的本地模板绝对路径 |
| 节点内容绑定 | `NodeContentBinding` | 记录某台节点针对某个 ArcadeGame 当前已准备/发布给新实例使用的 ContentVersion，以及该内容在该节点是否接受新实例 |

普通 VPK 内容更新：

```text
ContentVersion v1
→ ContentVersion v2
```

**不要求**同时产生新的 `TemplateRevision`。

ContentVersion 采用“新版本新增、旧版本保留”的不可变语义：

- 不通过原地覆盖 v1 文件把它“变成”v2；
- 每个 Allocation 创建时固定记录 `content_version_id`；
- 同一 Allocation 生命周期内不得因为节点后来切换了当前发布版本而静默改变 ContentVersion；

只有启动参数、cfg、Ready 判定等“启动语义”发生变化时，才创建新的 `TemplateRevision`。

## 3.3 节点与开服流程

| 中文称呼 | 代码名 | 含义 |
|---|---|---|
| 游戏节点 | `Node` | 一台能够运行 Node Controller、d2core 和 Dota 专服的机器 |
| 开服申请 | `ServerRequest` | 玩家/队伍提出“我要一个服务器”的业务意图，也是排队对象 |
| 资源分配记录 | `Allocation` | 记录这次申请占用了哪个节点资源，并最终关联哪个 d2core 实例 |
| 节点任务 | `NodeJob` | Platform Server 派给某台 Node Controller 的具体执行工作，例如 create/stop |
| 审计记录 | `AuditEvent` | 记录管理员或重要业务动作的历史 |
| 管理员 | `AdminUser` | 平台管理后台账号，与匿名玩家 User 分开 |
| 管理员会话 | `AdminSession` | 管理员登录后的独立会话 |
| 平台运行设置 | `PlatformSettings` | 保存全局是否接受新申请、维护提示等少量运行控制 |
| 站点公告 | `SiteAnnouncement` | 面向玩家显示的一条轻量公告/维护提示，不是完整 CMS |

最重要的关系：

```text
玩家点击“申请服务器”
        ↓
开服申请 ServerRequest
“我要一个服务器”
        ↓
平台选择节点并占用一个资源位
        ↓
资源分配记录 Allocation
“这次申请占用了 Node A 的一个名额”
        ↓
节点任务 NodeJob
“请 Node A 执行 create”
        ↓
d2core instance
真实专服实例
```

结束时：

```text
同一个 Allocation
        ↓
新的 NodeJob：stop
        ↓
d2core stop
        ↓
完整 reclaim
        ↓
结束 Allocation
```

因此：

```text
ServerRequest != NodeJob
NodeJob != Allocation
Allocation != d2core instance
```

V1 同时冻结以下关系不变量：

- `ServerRequest` 必须且只能有一个业务 owner：
  - 未加入 Party 的用户：owner = `User`；
  - 已加入 Party 的用户：正常开服 owner = `Party`，只有队长可提交；
  - 不允许同一 ServerRequest 同时以 User 和 Party 为 owner；
- 同一 owner 同时最多有一个**阻塞新的普通申请**的 ServerRequest；
- 重复点击/重复 POST 不创建第二条申请，而是返回该 owner 已存在的活动申请；
- 平台必须提供“查询我 / 当前 Party 的活动申请”的能力，用于浏览器响应丢失后的恢复；
- 一个 ServerRequest 可以产生零到多个**顺序 Allocation attempt**；
- 任意时刻最多一个 Allocation attempt 拥有当前调度权；
- Allocation 一旦创建，`node_id`、该 attempt 的 `content_version_id` 和关联 NodeJob 历史不得原地改写成另一个节点/版本；
- 安全重新调度时，结束旧 attempt 后创建新的 Allocation attempt，而不是覆盖旧记录；
- quarantined 后队长执行“放弃异常服务器并继续”只解除旧请求对 owner 的业务阻塞；旧 ServerRequest / Allocation / NodeJob 历史和资源占用记录必须保留。

# 4. 前置项目 d2core

前置项目：

```text
L4C99/dota2-arcade-dedicated-core
```

以下简称：

```text
d2core
```

平台 V1 固定依赖：

```text
Release: v0.1.1
Tag: v0.1.1
Commit: 988720ad85af1f0d97bfe98ec4da4fcbb070beea

protocolVersion = 1
template schemaVersion = 1
disk formatVersion = 2
```

平台不得依赖 d2core `main` 的未发布行为。

## 4.1 d2core 负责什么

- 本机 Dota 实例 create/restart/stop/reclaim；
- 配置快照；
- 本机端口分配；
- 进程身份校验；
- 日志；
- 持久化；
- **管理器重启后的实例恢复管理**；
- Windows Named Pipe / Linux Unix socket 本地协议。

其中 `restart` 是 d2core 自身已有的底层能力。**平台 V1 的正常业务流程不调用 d2core 实例 `restart`**；平台只依赖其存在不改变 d2core 自身的独立能力边界。


“管理器重启后的实例恢复管理”指：

```text
Dota 实例仍在运行
        ↓
d2core serve 崩溃或重启
        ↓
重新启动 d2core
        ↓
读取持久化记录 + 校验进程身份
        ↓
重新识别并继续管理原实例
```

## 4.2 平台负责什么

- 用户和队伍；
- 游廊游戏/玩法选择；
- 跨节点调度；
- 排队；
- 资源分配；
- 节点任务；
- 容量；
- 异常隔离；
- 玩家 Web UI；
- 管理员后台；
- 公网连接信息。

## 4.3 d2core 当前不提供

- TCP/HTTP 公网管理 API；
- 跨节点调度；
- 用户/队伍；
- Steam 登录；
- 玩家 SteamID/人数状态；
- 通用 Dota 控制台通道；
- `status_json` 自动查询接口；
- 自动地图/VPK 下载；
- 防火墙/NAT 自动配置；
- 公网连接地址推导；
- 自动空服回收；
- 平台业务数据库。

Node Controller 必须使用 d2core 正式 Go client / 本地 API，不得把 CLI 子进程作为正常集成方式，也不得绕过 d2core 自行管理 Dota 进程。

# 8. AGENTS.md 的定位

`AGENTS.md` 是给开发 AI 的短护栏，不是完整任务书。

应提醒：

- 固定 d2core v0.1.1；
- Platform Server 不直连 d2core；
- Node Controller 不绕过 d2core；
- timeout != failure；
- 已受理/可能有副作用的实例未完整 reclaim 不释放资源；只有明确证明 create 无副作用时才可走 released_no_effect；
- 可能已经产生实际副作用的节点任务不能因为没收到回复就自动改派；
- 不提交凭据、VPK、玩家日志；
- 不擅自扩大 V1。

例子：

```text
Platform 要求 Node A create
        ↓
Node A 已经调用 d2core
        ↓
此时网络断开
        ↓
Platform 不知道是否已经创建成功
```

如果此时直接派给 Node B，可能得到两台重复服务器。

正确做法：

```text
冻结该申请
→ 等 Node A 恢复并对账
→ 确认没有产生实例后
→ 才允许重新调度
```

# 10. HTTPS / TLS

```text

  │ localhost HTTP
  ▼
```

- Node Controller ↔ d2core 继续使用本机 Named Pipe / Unix socket，不使用 TLS。

# 11. 匿名身份与队伍

V1 不要求 Steam 登录。

首次访问：

- 创建稳定内部用户 ID；
- 创建服务端 Session；
- 浏览器保存不可预测会话凭证；
- 页面刷新、浏览器正常关闭重开、Web Server 重启后可恢复。

不解决：

- 清 Cookie 后找回原身份；
- 换设备自动找回。

未来 Steam 登录绑定现有 User，不把 SteamID 改成业务主键。

队伍是持久对象，不随一局结束自动消失。

统一称：

- 队长；
- 队员。

V1 不做队长转让。

## 11.1 Party membership 与请求 owner

V1 冻结：

- 一个 User 同时最多属于一个 Party；
- User 不在 Party 时，可以提交 User-owned 的 solo ServerRequest；
- User 已在 Party 时，正常开服申请归属于 Party，只有队长可提交；成员不再同时创建独立 solo 申请；
- 普通队员可随时退队，退队不停止 Party 已有实例；
- 有 blocking ServerRequest / Allocation 时，队长不能正常退队或解散 Party。

Party 自身成员硬上限来自：

```text
PlatformSettings.max_party_size
```

它是部署/运行设置，不与某个 GamePreset 的游戏内人数上限混为一谈。

GamePreset 另有：

```text
max_players
```

提交申请时必须满足：

```text
当前 Party 成员数 <= GamePreset.max_players
```

否则在创建 ServerRequest 前拒绝申请并给出明确提示。

`PlatformSettings.max_party_size` 的具体数值由部署方在 P2 前配置；migration/example config 必须要求一个显式正整数值，不在业务代码里隐藏硬编码默认。

## 11.2 队长/队员能力

队长可：

- 邀请/重置邀请链接；
- 移除成员；
- 选择游廊游戏；
- 选择玩法预设/难度；
- 选择自动/手动节点；
- 申请服务器；
- 取消**安全可取消**的等待请求；
- 结束服务器；
- 下一局；
- 空闲时解散队伍。

V1 对“安全可取消”的定义是：

> 只有仍处于纯 waiting、**尚未创建任何 Allocation attempt** 的 ServerRequest 才允许立即取消。

一旦已经产生 Allocation：

- 不再把该请求视为“安全可取消”；
- 不通过取消动作释放容量；
- 后续按 create/reconcile/stop/reclaim 或 quarantined 流程收敛。

普通队员可随时退队，退队不停止实例。

活动期间只要：

```text
Party 当前成员数 < PlatformSettings.max_party_size
```

仍允许新队员加入；加入后若人数超过当前 GamePreset 的 `max_players`，不得再提交该玩法的新申请，但不会自动停止已经存在的服务器。

有 waiting / allocating / creating / running / stopping / unknown 等 blocking 活动时，队长不能正常退队或解散。

# 12. 游廊游戏、玩法、内容与模板

## 12.1 游廊游戏（ArcadeGame）

一个玩家可选择的游廊/Workshop 内容。

至少区分两个运行控制：

- `enabled`：是否作为平台正式提供的内容。关闭时通常从普通玩家列表隐藏，适合长期下架；
- `accepting_new_requests`：当前是否接受新的开服申请。关闭时仍可显示，但应标记“维护中/暂不可申请”。

可附带：

- `maintenance_message`：该游戏暂停申请时给玩家看的原因说明。

每个 ArcadeGame 还必须有一个平台级发布指针：

```text
current_content_version_id
```

语义：

> 这是**下一次新建 Allocation attempt** 应使用的正式 ContentVersion。

它必须指向该 ArcadeGame 已存在的 ContentVersion。

只有在对应版本至少已经在目标节点完成准备、真实验证并达到发布条件后，管理员才允许切换该指针；切换必须写 AuditEvent。

## 12.2 玩法预设（GamePreset）

同一 ArcadeGame 下不同的玩法、难度或服务器配置，例如：

```text
ArcadeGame: 某游廊地图
GamePreset:
├─ N6
├─ N7
└─ Solo
```

GamePreset 可决定：

- `max_players`；
- TemplateRevision；
- 支持节点等。

其中 `max_players` 表示该玩法允许的玩家/Party 人数上限，不是节点“最多可开几台实例”的容量字段。

GamePreset 同样至少区分：

- `enabled`：是否正式提供；
- `accepting_new_requests`：是否临时接受新申请；
- `maintenance_message`：该玩法暂停申请时的提示。

因此可以只暂停某个玩法，而不影响同一游廊游戏下的其他玩法。

## 12.3 内容版本（ContentVersion）

表示某一版实际服务端内容。

普通 VPK 更新产生新 ContentVersion。

ContentVersion 是不可变对象：

- 新内容创建新 ContentVersion；
- 不通过原地覆盖旧 release 目录把 v1 “变成” v2；
- 已被 Allocation 记录引用的版本 ID 不修改其含义。

## 12.4 模板修订版（TemplateRevision）

表示一版 d2core 启动配置。

普通 VPK 内容变化不要求新模板；只有启动语义变化时才需要新 TemplateRevision。

## 12.5 节点模板映射（NodeTemplateBinding）

例如：

```text
Windows:
n7-r3 → D:\d2core\templates\n7-r3.json

Linux:
n7-r3 → /srv/d2core/templates/n7-r3.json
```

Platform Server 不直接指定任意本机路径，Node Controller 只接受预先配置的逻辑模板映射。

某次 create NodeJob 真正执行前，Controller 解析出的具体本机模板绝对路径必须作为该 NodeJob 的冻结执行参数持久化；后续重试不能因为 NodeTemplateBinding 后来变化而换成另一条路径。

# 14. 节点公网与 NAT 模型

不要求每个节点有独立公网 IP。

合法场景：

```text
A. 独立公网 IP
B. 公网 IP + 域名
C. 厂商 NAT，只给公网域名和映射端口
D. 共享公网出口，外部端口与本地端口完全不对称
```

`connect_host` 是玩家普通连接实际使用的地址，可为：

- IP；
- 自有域名；
- 厂商 NAT 域名。

`protocol_ip` 只用于经过验证的一键协议入口，可以为空。

如果只有厂商 NAT 域名，不得自动 DNS 解析后假定可用于 Steam URI。

# 15. 本地游戏端口与公网映射

本地游戏端口不固定为 27015 左右。

节点可以配置任意合适的 d2core 本地端口池。

具体实例仍由 d2core 自动分配，平台不实现第二套端口分配器。

NAT/端口映射的权威配置保存在 Node Controller 本地。

V1 支持：

```text
identity
explicit
```

### identity

```text
28000 → 28000
28001 → 28001
```

### explicit

```text
28000 → 45123
28001 → 46781
28002 → 49210
```

适用于厂商 NAT，也适用于拥有独立公网 IP 但主动使用非对称 NAT 的节点。

示例：

```yaml
network:
  connect_host: nat-node.provider.example
  protocol_ip: ""

  local_game_port_range:
    min: 28000
    max: 28002

  public_port_mapping:
    mode: explicit
    mappings:
      28000: 45123
      28001: 46781
      28002: 49210
```

## 15.1 端口池配置源

d2core v0.1.1 的本地 API 不提供“读取 manager 当前 `--port-min/--port-max`”的管理查询。

因此 V1 不假设 Controller 能从 API 反查实际端口池。

必须把以下内容视为**部署不变量**：

> Node Controller 的 `local_game_port_range` 与 d2core serve 的 `--port-min/--port-max` 来自同一份节点部署配置或同一配置生成流程。

Controller 启动时负责验证：

- 声明的每个本地端口都存在公网映射；
- `hard_max_instances` 不大于声明端口池可用端口数量；
- mapping 中不存在重复/非法项。

P0/P5 的安装验证还必须检查实际 systemd / Windows service 的 d2core serve 启动参数与这份部署配置一致。

如果运维绕过部署流程手工修改 d2core serve 端口范围，该节点应先 Drain 并重新执行配置验证，而不是假定 Controller 能自动发现差异。

## 15.2 实际实例端口与 JoinInfo

Controller 必须以 d2core 对**具体实例实际报告的本地游戏端口**做 mapping 查表。

不得仅根据“理论端口池”猜测公网端口。

如果某个 Ready 实例的实际本地端口没有对应公网映射：

- 不得生成假的 `connect` / Steam / steamchina 地址；
- 不得把该实例报告为“进房信息可用”；
- 必须向 Platform 上报结构化 join-info 错误；
- Allocation 仍按真实实例状态占用容量，不能因为“没有连接信息”直接释放。

公网连接信息由 Controller 根据节点本地权威网络配置生成/确认后上报 Platform；Platform 负责展示，不从可能过期的数据库字段自行猜测实例公网端口。

# 16. 玩家进房与 A2S

玩家正常优先使用一键入口，`connect` 是永久兜底。

普通 connect：

```text
connect <host>:<port>
```

已知支持：

- IP；
- 域名；
- 实际公网/NAT 端口；
- 不依赖 A2S。

Steam：

```text
steam://connect/<IP>:<PORT>
```

蒸汽平台：

```text
steamchina://connect/<IP>:<PORT>
```

标准正式节点默认应配置 A2S。

Node Controller 上报节点部署事实与实例诊断：

```text
a2s_enabled
每个 Ready 实例的 A2S 查询状态与 checked_at
```

`a2s_enabled` 表示节点部署配置启用了 A2S 相关能力。Controller 仅查询当前 `lifecycle=active`、`process=running`、`room=ready` 的本地实例，分别记录 Node、实例、实际本地端口、`ok/failed` 与检查时间；尚未查询必须与失败区分。没有 Ready 实例就没有实时 A2S 查询事实。旧聚合 `a2s_query_ok` 仅为兼容保留的派生值，不是节点或入口健康状态。

但：

```text
A2S 能查询
!=
真实客户端一定能一键进房
```

非对称 NAT 下可能出现 A2S 查询成功但一键入口失败。

因此不得仅凭 A2S 查询向玩家开放一键按钮。

A2S 查询是管理员实例/Allocation 详情的后台诊断，不进入玩家 API、JoinInfo 或页面，也不是端口池覆盖认证，不参与普通 `connect`、玩家一键按钮、节点容量或调度资格判断。瞬时查询失败不自动改变真人验证或已开放的入口。

## 16.1 `connect` 手动进房帮助

`connect` 是永久兜底，因此前端不能只给出一条命令而假设玩家已经会使用 Dota 2 控制台。

Ready 页面至少提供：

- 可直接复制的 `connect <host>:<port>`；
- 易发现但不干扰主流程的“如何使用 / 手动进房帮助”入口；
- 如何启用并打开 Dota 2 控制台；
- 在控制台粘贴并执行平台生成的 `connect` 命令；
- Steam / 蒸汽平台一键入口失败时，明确引导玩家改用该方式。

具体按钮布局、教程展开方式、截图和最终文案在 P-1 / P1 阶段确定，不在本任务书中写死。

“如何启用/打开控制台”的最终步骤必须在当时的真实 Dota 2 客户端上复核后再写入前端帮助和用户文档，避免长期规格固化过时 UI 步骤。

# 17. 一键入口：验证与开放分离

Steam 和蒸汽平台分别保存：

```text
steam_entry_verified
steam_entry_enabled

steamchina_entry_verified
steamchina_entry_enabled
```

`*_verified`：

> 已认证管理员明确确认，在当前 Node、当前 `entry_config_revision` 下，已使用对应真实 Steam / 蒸汽平台客户端，通过一键 URI 成功进入一个真实 Ready 游戏实例。

它是**人工实测确认结果**，不是 A2S 查询结果，也不是实时探测结果。

`*_enabled`：

> 是否允许玩家前端显示对应一键按钮。

规则：

```text
未 verified → 不允许 enabled
verified → 管理员可选择 enabled / disabled
```

平台还应记录：

- 验证时间；
- 验证管理员；
- 对应的 `entry_config_revision`（或等价 fingerprint）。

确认真人验证必须二次确认并写入 Audit；不要求端口列表、逐端口覆盖或必填备注。Steam 与蒸汽平台必须分别确认，不能相互推导。同一 revision 内 `verified` 只由管理员从 false 确认为 true，V1 不提供普通撤销验证操作。入口异常时管理员关闭 `enabled`；只有入口配置 revision 变化才自动清除两种 scheme 的验证、开放与当前验证元数据。

`entry_config_revision` 至少由会影响一键入口的网络事实形成，例如：

- `protocol_ip`；
- 本地/公网端口映射**完整集合**；
- 与协议入口有关的 A2S 配置。

完整 mapping 纳入 revision 是为了标识被管理员验证的网络配置，不要求对每个端口真人进入。关键入口网络事实发生变化时，revision 改变，两个 scheme 的旧验证立即失效，平台自动：

```text
verified = false
enabled = false
```

重新要求真人验证。

普通 Platform/Web 发布、Platform/Controller/d2core manager 重启、VPK/ContentVersion 更新和普通实例创建/结束，在入口网络事实未变化时本身不要求重新真人验证。玩家 URI 仍必须满足 Ready、有效 JoinInfo、`protocol_ip`、当前 revision 与对应 scheme 的 `verified && enabled`；当前 A2S 查询结果不作为额外门槛。`connect` 继续作为正式兜底。节点后台只显示 A2S 配置事实；实例后台显示逐实例查询结果。

# 19. ContentVersion、版本目录与节点内容绑定

## 19.1 V1 的正式边界

V1 的 ContentVersion 发布以**游戏节点（Node）作为内容隔离边界**。

也就是说：

> 同一节点、同一 ArcadeGame 在 V1 的正常运行中只把一个 ContentVersion 作为“当前给新实例使用的节点本地版本”。

V1 **不支持也不依赖**：

> 同一节点里，活动实例 A 继续使用 v1，而新实例 B 同时使用 v2。

因此全局目录链接/Junction 的职责是：

> **版本组织、当前节点发布版本指针和快速回滚。**

它不是活动实例的热切换机制。

## 19.2 NodeContentBinding

平台保存节点内容绑定（`NodeContentBinding`），至少表达：

```text
node_id
arcade_game_id
reported_content_version_id
reported_state
reported_at
accepting_new_allocations
```

例如：

```text
Node A
├─ Game 123 → reported v2 / accepting=true
└─ Game 456 → reported v5 / accepting=true

Node B
├─ Game 123 → reported v1 / accepting=false
└─ Game 456 → reported v5 / accepting=true
```

这里必须严格区分**节点事实**和**平台调度控制**：

### 节点事实

`reported_content_version_id` / `reported_state`：

- 表示节点磁盘上当前实际发布给该 ArcadeGame 的版本；
- 权威来源在节点本地 ContentRoot / 当前链接 / metadata；
- 由 Node Controller 读回并上报；
- Platform 管理员不能只修改数据库就宣称节点已经从 v1 变成 v2；
- Controller 无法确认时，状态为 unknown，该绑定不可用于新 Allocation 调度。

P5 的 Content Tool 负责安全修改链接和 metadata；Controller **不自动调用 Content Tool**，只负责读取事实并上报。

### 平台调度控制

`accepting_new_allocations`：

- 是 Platform 侧的调度开关；
- 管理员可暂停/恢复某个 `Node × ArcadeGame` 接受新的 Allocation；
- 不修改节点磁盘内容；
- 不停止已有 Allocation。

因此 `NodeContentBinding` 是：

> “节点实际内容事实的最近确认快照 + 平台是否允许继续向该节点该内容派新 Allocation 的控制”。

数据库实现不得把“一个 Node + ArcadeGame 永远只能存在一个 ContentVersion”写成未来无法扩展的永久架构假设；V1 只要求一个被报告为当前版本。

## 19.3 当前发布版本与 Allocation 固定版本

平台级：

```text
ArcadeGame.current_content_version_id
```

是**新 Allocation attempt 的版本目标**。

V1 的版本冻结点是：

> **Allocation 创建时，而不是 ServerRequest 创建时。**

因此：

- waiting ServerRequest 不固定 ContentVersion；
- 调度器准备创建新的 Allocation attempt 时，先读取 ArcadeGame 当前发布版本；
- 在同一个调度事务里把该值复制到 `Allocation.content_version_id`；
- 之后该 Allocation 生命周期内不得静默改变；
- 节点必须存在 `reported_content_version_id == Allocation.content_version_id` 且 `accepting_new_allocations=true` 的 NodeContentBinding 才可被选择；
- 如果一个旧 Allocation 已被证明无副作用并安全结束，后续新的 Allocation attempt 可以使用届时新的 `current_content_version_id`；
- V1 平台业务流程不使用 d2core 实例 `restart`；
- “下一局”通过 `stop → 完整 reclaim → 新 ServerRequest → 新 Allocation → create` 实现，因此新一局自然使用届时正式发布的 ContentVersion。

这样在滚动发布期间，已经 waiting 的请求不会被永远锁在旧版本；真正开始占用节点资源时才冻结准确版本。

如果未来引入同一 Allocation 的重新启动语义或 per-instance content isolation，必须届时重新定义版本保持规则，不得在 V1 中提前假设。

# 20. VPK 版本目录与 Content Tool

## 20.1 版本仓库布局

推荐把版本仓库放在 Dota 安装目录之外：

```text
<ContentRoot>/
└─ <WorkshopID>/
   ├─ releases/
   │  ├─ v1/
   │  │  └─ pak01_dir.vpk
   │  └─ v2/
   │     └─ pak01_dir.vpk
   └─ metadata/
      ├─ v1.json
      └─ v2.json
```

版本元数据放在 `metadata/`，不要塞入 Dota 实际 addon 根目录。

Dota 实际识别入口：

```text
<DotaRoot>/game/dota_addons/<WorkshopID>
```

V1 推荐让**整个 Workshop ID 目录**指向当前 release：

```text
<DotaRoot>/game/dota_addons/123
                    │
                    └────→ <ContentRoot>/123/releases/v2
                                               │
                                               └─ pak01_dir.vpk
```

不是只给 `pak01_dir.vpk` 文件本身建立链接。

历史版本、非当前资源、平台 metadata 不放进实际 `dota_addons/<WorkshopID>` 根目录，避免依赖 Dota 是否会扫描额外文件/子目录这一未验证行为。

## 20.2 软链接/Junction 的语义

Linux 可采用目录 symlink；Windows 可采用 Directory Junction 或经验证的目录 symlink。

正式语义：

> 目录链接只用于“这个节点当前把哪个版本发布给新实例”，不保证活动实例期间切换链接仍能让旧实例永久保持旧版本。

因此 V1 的 `switch` 只能在目标内容已经完成排空后执行。

## 20.3 Content Tool

由于游廊内容更新属于正常运维需求，平台仓库规划 `content-tool`，与 Platform Server、Node Controller 同仓。

V1 后段最小命令：

```text
content-tool status <WorkshopID>
content-tool prepare <WorkshopID> <version> <source-vpk>
content-tool switch <WorkshopID> <version>
content-tool rollback <WorkshopID>
```

职责：

- `status`：显示当前目录指向、已准备版本和必要元数据；
- `prepare`：准备不可变 release、检查 VPK、计算 SHA256/大小、写 release 外部 metadata；
- `switch`：在运维已经确认安全后，把整个 Workshop ID 目录切到目标 release，原子更新可由 Controller 读回的当前版本 metadata，并读回确认；
- `rollback`：恢复上一个已知目录指向。

明确不做：

- 自动下载 Workshop/VPK；
- 自动 Drain；
- 自动判断是否还有活动实例；
- 被 Node Controller 自动调用；
- 实现运行中 per-instance 热切换。

平台负责生命周期安全，Content Tool 负责文件操作安全。

具体 Windows/Linux 链接命令必须经过对应平台真实验证后写入部署文档。

# 21. 内容发布：单节点排空与多节点滚动

V1 的正式发布动作由两个事实共同决定：

- `ArcadeGame.current_content_version_id`：平台“新 Allocation 要用哪一版”的权威指针；
- `NodeContentBinding.reported_content_version_id`：某个节点“磁盘上实际已经是哪一版”的节点事实。

只有二者匹配且该 Binding `accepting_new_allocations=true` 时，节点才可接该游戏的新 Allocation。

## 21.1 内容验证实例：V1 的最小维护方式

本任务书要求“切换后创建测试实例并真人验证”，但 V1 不为此新增一个管理员任意开服系统。

V1 采用以下**明确的维护例外**：

> 在目标节点已经 Node Drain、不会再接收任何新的平台 Allocation 的窗口内，运维人员可以在节点本地使用 d2core 官方 CLI / client 手工创建一个临时验证实例。

该做法：

- 只允许用于明确的内容/Dota/A2S 维护验证；
- 不是 Node Controller 的正常集成方式；
- 不允许由 Web 后台执行任意 CLI；
- Node Drain 期间已有正常实例可以继续运行，但平台不会再向该节点派新 Allocation；
- 验证实例必须使用目标 ArcadeGame/GamePreset 对应的正式 TemplateRevision，并明确验证刚切换的 ContentVersion；
- 该临时实例不进入 Platform Allocation 统计，因此 **Node Drain 是强制前提**，不得在仍接受新 Allocation 的节点上这样做；
- 验证实例必须由运维显式 stop，并确认 d2core 已完整 reclaim；
- Controller 随后执行 `list/status` resync，确认临时验证实例已不存在/已完整回收；
- 在完成上述确认前不得解除 Node Drain。

这样不会让平台在不知道验证实例存在时继续向节点分配新资源，也不需要为 V1 新增“管理员任意 create”产品能力。

## 21.2 单节点

如果只有一个承载该 ArcadeGame 的节点：

```text
1. ArcadeGame/GamePreset 进入内容维护，暂停新申请与 waiting 调度
2. NodeContentBinding.accepting_new_allocations = false
3. 等该节点上相关 Allocation 全部正常结束/回收
4. content-tool prepare
5. content-tool switch 到 v2
6. Controller resync/readback，确认 reported_content_version_id = v2
7. 临时 Node Drain
8. 按 21.1 创建本地验证实例，真人验证 VPK/进房；stop 并确认完整 reclaim
9. Controller 再次 resync
10. 解除 Node Drain
11. 将 ArcadeGame.current_content_version_id 切到 v2（AuditEvent）
12. NodeContentBinding.accepting_new_allocations = true
13. 解除内容维护
```

这是正式 V1 的 Content-level Drain。

## 21.3 双节点/多节点滚动发布

初始：

```text
ArcadeGame.current_content_version_id = v1
Node A reported v1 / accepting=true
Node B reported v1 / accepting=true
```

发布 v2：

```text
1. Node A 的该 ArcadeGame：accepting_new_allocations=false
2. 等 Node A 上该游戏的旧 Allocation 全部结束/回收
3. Node A prepare + switch v2
4. Controller 确认 Node A reported v2
5. 临时 Node Drain A，按 21.1 做本地验证实例；完整 stop/reclaim 后 resync，再解除 Node Drain
6. Node A 的该 ArcadeGame：accepting_new_allocations=true
   （此时全局 current 仍为 v1，版本不匹配，所以 Game 123 仍不会被调度到 A）
7. 将 ArcadeGame.current_content_version_id 切到 v2
8. 从这一刻开始，新 Allocation 只会进入已 reported v2 的 Node A
9. Node B 的该 ArcadeGame：accepting_new_allocations=false
10. Node B 上已经存在的 v1 Allocation 继续运行直到结束
11. Node B prepare + switch v2
12. Controller 确认 Node B reported v2
13. 临时 Node Drain B，完成本地验证实例并完整 reclaim/resync，再解除 Node Drain
14. Node B 的该 ArcadeGame：accepting_new_allocations=true
```

过渡期间允许：

```text
Node A = v2
Node B = v1
```

已有 v1 Allocation 不因发布被停止；新的 Allocation 在第 7 步之后只使用 v2。

waiting ServerRequest 不提前绑定版本，因此会在真正获得 Allocation 时使用当时的 `current_content_version_id`。

`current_content_version_id` 的切换是管理员明确发布动作，必须记录 AuditEvent；它不会修改任何已经存在的 Allocation。

## 21.4 与全局/内容/节点维护的关系

- 单节点没有可替代容量时，用 ArcadeGame/GamePreset 内容维护暂停该内容；
- 多节点滚动更新时，优先用 `NodeContentBinding.accepting_new_allocations=false` 做 `Node × ArcadeGame` 级排空；
- Node Drain 仍用于整台机器维护，以及本节 21.1 的短时本地验证窗口；
- 任何维护开关都不自动停止已有实例。

## 21.5 后续每实例内容隔离的架构预留（非 V1）

未来可以独立研究：

> **每实例内容隔离（per-instance content isolation）**

目标：

```text
旧 Allocation A → 固定 ContentVersion v1
新 Allocation B → ContentVersion v2
A/B 在同一节点同时运行
```

当前只保留以下边界：

- ContentVersion 是独立不可变版本对象；
- Allocation 固定记录 `content_version_id`；
- NodeContentBinding 的数据库设计不得永久阻止未来同节点多版本扩展；
- 未来 Linux/Windows 底层实现允许不同；
- 是否支持由未来节点 capability 决定。

已有旧 Linux 平台实践表明，基于 systemd mount namespace / bind mount 存在每进程/服务内容视图的可行方向；但尚未验证与 d2core v0.1.1 的进程身份、recovery 和 cleanup 等完整生命周期兼容。

Windows 的每实例文件系统隔离路径尚未验证。

因此：

> 该能力不属于 V1，不得阻塞 V1，也不得在 V1 中提前实现未经验证的 mount namespace、文件系统虚拟化或 d2core 扩展。

# 23. 资源调度与服务可用性

## 23.1 Node 容量与 Allocation 状态

Node Controller 报告本地绝对上限：

```text
hard_max_instances
```

平台管理员设置当前调度上限：

```text
desired_max_instances
```

要求：

```text
0 <= desired_max_instances <= hard_max_instances
```

Platform API 对超出 hard max 的 desired 值应拒绝；如果节点后续上报更小的 hard max，使历史 desired 暂时高于 hard，则调度器仍按实际较小值保护，不继续突破本地上限。

调度器无论如何都按：

```text
occupied < min(hard_max_instances, desired_max_instances)
```

判断实例容量。

### Allocation 最小状态语义

V1 至少区分：

| Allocation 状态 | 占容量 | 是否资源终态 | 说明 |
|---|---:|---:|---|
| `reserved` | 是 | 否 | 已选择 Node 并原子预留容量，尚未确认 d2core side effect |
| `create_unknown` | 是 | 否 | create 调用结果未知，必须 reconcile |
| `creating` | 是 | 否 | instanceId/operationId 已知，实例正在创建/启动 |
| `running` | 是 | 否 | 实例仍存在并由平台托管；Ready 由 d2core `room` 状态另行判断 |
| `stopping` | 是 | 否 | 正在 stop/reclaim |
| `failed_unreclaimed` | 是 | 否 | create/运行失败，但底层实例/资源尚未完整回收 |
| `quarantined` | 是 | 否 | 自动流程无法确认安全回收，等待管理员后续处理 |
| `reclaimed` | 否 | 是 | d2core 已确认 `reclaimed + stopped + cleanup complete` |
| `released_no_effect` | 否 | 是 | 已证明本次 create 没有产生 d2core 实例副作用 |

因此正常已受理实例只有在：

```text
lifecycle = reclaimed
process = stopped
cleanup = complete
```

后才能进入 `reclaimed` 并释放容量。

但 create 还存在另一条合法释放路径：

> 如果 d2core **明确无副作用拒绝** create，或对 unknown 完成对账后明确证明没有产生任何对应实例，则 Allocation 可以进入 `released_no_effect` 并释放预留。

“明确无副作用”至少要求：

- 收到结构化拒绝且没有 instanceId/operationId，且不存在响应丢失歧义；或
- 经过 `list` / operation / status 对账后，能够正面确认该 NodeJob 没有产生对应实例。

只要 create 已被受理、已有 instanceId、或 side effect 仍为 unknown：

> 不得走 `released_no_effect`。

如果 create operation 最终失败但实例记录仍存在，Allocation 进入 `failed_unreclaimed`，平台应自动发起 stop/reclaim；无法安全收敛时进入 quarantined。

### NodeJob 最小状态语义

NodeJob 至少区分：

| NodeJob 状态 | 是否终态 | 含义 |
|---|---:|---|
| `pending` | 否 | 已持久化，尚未被 Controller 领取 |
| `claimed` | 否 | Controller 已领取/准备执行 |
| `accepted` | 否 | d2core 已返回 operationId/instanceId，等待 operation 收敛 |
| `unknown` | 否 | 调用结果未知，必须 reconcile，不能当失败重新 create |
| `succeeded` | 是 | 本 NodeJob 对应操作已确认成功终结 |
| `rejected_no_effect` | 是 | 明确未产生 d2core 实例副作用 |
| `failed_with_effect` | 是 | 本 Job 已失败/终结，但 Allocation 仍有底层实例或资源需要 stop/reclaim/quarantine |

NodeJob 的终态不等于 Allocation 的资源终态。

## 23.2 请求 owner、重复提交与安全取消

调度队列单位是：

> 一个 User/Party owner 的一次 ServerRequest。

同一 owner 同时最多一个 blocking ServerRequest。

浏览器连续点击、网络重试或重复 POST：

- 不创建第二条 ServerRequest；
- 返回已经存在的 blocking request 及其当前状态；
- HTTP 具体状态码由 API 文档决定，但业务语义必须是“返回原申请”，不是创建新申请或仅报一个无法恢复的错误；
- 数据库层必须使用唯一约束、事务串行化或等价机制保证并发下也成立。

平台提供“查询当前 owner 活动申请”接口，用于刷新/响应丢失恢复。

**安全取消**只允许：

```text
ServerRequest = waiting
AND
不存在任何 Allocation attempt
```

取消后该请求成为终态，不占容量。

一旦已经创建 Allocation，取消入口关闭；后续使用正常生命周期或异常收敛，不允许通过“取消”释放已预留/可能已有副作用的资源。

如果用户要修改手动节点选择：

> 只能在安全可取消的 waiting 阶段取消旧请求后重新提交，因此获得新的 `requested_at`，不保留原队列位置。

## 23.3 FIFO 与节点选择

V1 FIFO 定义为：

> 在当前可被实际调度的 waiting ServerRequest 中，选择 `requested_at` 最早者。

暂时不 eligible 的请求：

- 保留自己的 `requested_at`；
- 不阻塞与它没有资源竞争关系的其他请求。

例如：

- 手动等待已满的 Node A，不阻塞可使用 Node B 的自动请求；
- 某内容处于维护，不阻塞其他 ArcadeGame；
- 手动节点当前版本未更新，等待该同一节点后续恢复，不偷偷迁移。

自动请求在确定目标 ContentVersion 后，从 eligible Node 中按 priority 选择。

手动节点：

- 只考虑指定 Node；
- 不自动迁移；
- 可以继续显示“等待该节点容量/维护/版本同步”原因。

## 23.4 唯一调度资格谓词

创建 Allocation attempt 时，调度器必须在同一事务/锁边界内：

1. 读取 ArcadeGame `current_content_version_id`；
2. 找到满足全部条件的 Node；
3. 原子占用容量；
4. 创建 Allocation，并把该版本复制到 `Allocation.content_version_id`。

Node 至少必须满足：

```text
global_accepting_new_requests
AND ArcadeGame.enabled
AND ArcadeGame.accepting_new_requests
AND GamePreset.enabled
AND GamePreset.accepting_new_requests

AND Node.enabled
AND Node.accepting_new_requests
AND Node online
AND Node 未 Drain
AND Node 支持目标 GamePreset / TemplateRevision
AND Node Controller / d2core 版本与 V1 契约兼容

AND NodeContentBinding.reported_state = confirmed
AND NodeContentBinding.reported_content_version_id = ArcadeGame.current_content_version_id
AND NodeContentBinding.accepting_new_allocations = true

AND occupied < min(hard_max_instances, desired_max_instances)
```

所有派发路径（自动、手动、安全重调度）都必须复用同一 eligibility 逻辑，不能各自遗漏条件。

## 23.5 四类维护/暂停控制

### 全局维护

```text
global_accepting_new_requests = false
global_maintenance_message = "..."
```

效果：

- 网站、Session、Party、已有实例、管理员后台继续可用；
- 不允许新的 ServerRequest；
- 已 waiting 的请求暂停调度并保留队列时间；
- 已有 Allocation 不自动停止。

### 内容维护

ArcadeGame / GamePreset：

```text
enabled = true
accepting_new_requests = false
maintenance_message = "..."
```

效果：

- 新请求被拒绝；
- 已 waiting 且尚无 Allocation 的对应请求暂停调度，保留 `requested_at`；
- 已有 Allocation 不自动停止；
- 其他内容不受影响。

### 下架（enabled=false）

`enabled=false` 表示不再正式提供，而不是临时维护。

因此：

- 不允许新请求；
- 对应仍处于纯 waiting、尚无 Allocation 的请求应终结并提示“内容/玩法已下架或不可用”，不得继续 dispatch；
- 已经有 Allocation 的实例不因下架自动停止，仍按正常 stop/reclaim 收敛。

### Node Drain

- 不再向该 Node 创建新的 Allocation；
- 已有实例继续；
- 自动调度可选择其他 Node；
- 手动指定该 Node 的 waiting 请求继续等待，除非用户在安全 waiting 阶段取消后改选。

### Node × ArcadeGame 排空

通过：

```text
NodeContentBinding.accepting_new_allocations = false
```

只暂停某个 Node 上某个 ArcadeGame 的新 Allocation。

用途主要是 P5 内容滚动发布，不影响该 Node 的其他 ArcadeGame。

所有维护/Drain 控制都不自动等价于 stop 已有实例。

## 23.6 轻量公告

V1 提供一条轻量站点公告，不建设 CMS。

至少支持：

```text
enabled
level: info / warning / maintenance
message
```

显示位置以 P-1 UI 审阅为准，一般位于玩家页面明显位置。

用途例如：

- Dota 2 今日更新，专服正在维护；
- 某游廊地图已更新，当前暂停新申请；
- 临时网络维护。

内容级维护信息优先显示对应 ArcadeGame/GamePreset 自己的 `maintenance_message`。

# 24. Node Controller 与 d2core

Node Controller：

- 与 d2core 同机；
- 同一普通 OS 用户；
- 使用正式本地 API；
- 不直接管理 Dota 进程；
- 不把 d2core CLI 子进程作为正常在线集成方式；
- 不负责自动调用 Content Tool。

Node 本地/部署配置至少包括：

- Platform URL；
- Node ID / Node Secret；
- d2core install/bin 位置（用于读取固定 Release 的构建元数据）；
- d2core data-dir；
- d2core/local game port range；
- hard max；
- connect_host；
- protocol_ip；
- public port mapping；
- A2S 部署声明/查询配置；
- Template bindings；
- ContentRoot / Workshop 内容 metadata 位置。

## 24.1 d2core 固定版本兼容约束

固定 d2core v0.1.1 的节点部署必须遵守：

- d2core data-dir、模板路径以及模板引用的关键本机路径使用该版本支持的 **ASCII 绝对路径**；
- 可以包含空格，但不要依赖非 ASCII 路径；
- d2core 对某些 cfg/受管目录存在链接祖先安全检查，因此 `data-dir` / cfg 等核心受管路径不得放在 ContentVersion symlink/Junction 结构之下；
- ContentVersion 的目录链接只用于 Dota `game/dota_addons/<WorkshopID>` 内容入口，不拿来承载 d2core data-dir/cfg。

具体路径限制以固定 v0.1.1 文档/实现为准；P0/P5 部署验证必须覆盖 Windows/Linux。

## 24.2 d2core 版本与协议上报

d2core v0.1.1 本地 API没有独立的 manager `version` 查询方法，因此 Node Controller 不应每次心跳 fork CLI。

V1 采用：

- `d2core_version`：从固定 Release 随包 `BUILD.json`（或等价正式构建元数据）读取；不可读时上报 `unknown`；
- `d2core_protocol_version`：按固定契约期望为 `1`，并以成功建立 protocol v1 本地连接为兼容依据；
- 版本未知、与冻结 Release 明显不符、或 protocol 不兼容时，节点不得继续接受新的 Allocation，管理员后台显示明确告警。

## 24.3 网络与内容事实

以下事实的权威在节点本地配置/磁盘：

- `connect_host`；
- `protocol_ip`；
- public port mapping；
- A2S 部署状态；
- 当前 ContentVersion metadata。

Controller 负责验证、读回并上报快照。

Platform 数据库中的这些字段用于展示和调度，不允许管理员通过纯数据库/纯 Web 修改就伪造“节点本地已经改变”的事实。

`NodeContentBinding.accepting_new_allocations` 例外：它是 Platform 调度控制，不代表磁盘变化。

## 24.4 端口范围的部署一致性

Node Controller 配置里的 `local_game_port_range` 与 d2core serve `--port-min/--port-max` 必须由同一份部署配置生成/维护。

Controller 只验证其声明范围和 NAT mapping；P0/P5 安装验收负责核对实际服务启动参数。

这些主要是新节点部署和新增玩法时的低频维护，不要求因此修改 d2core。

# 25. Create 幂等、冻结执行参数与结果未知

平台生成稳定：

```text
server_request_id
node_job_id
```

## 25.1 d2core create idempotencyKey

create NodeJob 的 d2core：

```text
idempotencyKey
```

必须在 Controller 完全丢失内存状态后仍能确定性恢复。

V1 冻结为：

> `idempotencyKey` 与不可变 `node_job_id` 一一确定性派生；不得每次执行随机生成新 key。

实现可以直接使用符合 d2core 协议约束的 NodeJob ID 或其确定性编码，但同一个 NodeJob 永远得到同一个 key。

## 25.2 首次调用前冻结 d2core create 请求

Node Controller 领取 create NodeJob 后：

1. 从本地 `NodeTemplateBinding` 解析具体模板绝对路径；
2. 构造本次 d2core protocol v1 create 的完整请求参数；
3. 在**第一次调用 d2core 之前**，把以下执行事实写回 Platform 的 durable NodeJob execution record：
   - `core_idempotency_key`；
   - resolved template absolute path；
   - port 请求值；
   - 其他会进入 d2core create 请求指纹的固定参数；
4. Platform 确认持久化后，Controller 才允许真正调用 d2core。

这些本机绝对路径只能由 Controller 根据可信 NodeTemplateBinding 产生；Web/Admin 不得提交任意路径。

同一 NodeJob 的后续重试：

- key 不变；
- resolved template path 不变；
- port 请求不变；
- 其他冻结参数不变。

因此即使 Controller 重启期间 NodeTemplateBinding 被运维改到了另一条路径，原 NodeJob 仍使用首次冻结的执行参数，不重新解析成另一份请求。

## 25.3 timeout / accepted

timeout：

> **结果未知，不等于未创建。**

不得换新 key 重复开房。

d2core `accepted` 只代表受理。

必须：

```text
保存 instanceId / operationId
→ 轮询 operation terminal
→ 再读取 status
```

如果调用响应丢失，NodeJob 进入 `unknown`，按 §26 对账。

无副作用拒绝与已受理失败的容量处理按 §23.1 两分支执行。

平台 V1 不调用 d2core 实例 `restart`。

# 26. Controller 重启、长时间断联与对账

“对账（reconcile）”指：

> Controller 启动、重启或节点恢复连接后，把 Platform durable NodeJob/Allocation 与 d2core 真实状态重新核对。

顺序：

```text
连接 d2core
→ list
→ 拉取本节点未终结 NodeJob / Allocation
→ 使用已冻结的 NodeJob execution record
→ operation/status
→ 上报事实
→ 收敛 unknown
→ 再领取新的普通任务
```

不得因 Controller 重启重复 create。

如果存在 `unknown` create：

- 优先通过 `list`、已知 instanceId/operationId、固定 idempotencyKey 和 status 查明事实；
- 在确认原任务不存在副作用前，不创建替代实例；
- 确认无副作用后才允许旧 Allocation `released_no_effect`，随后由同一 ServerRequest 产生新的 Allocation attempt。

d2core 的历史 operation / create-key 记录存在保留期限，因此节点经历很长时间断联后：

> 不能仅凭“我还记得旧 idempotencyKey”直接再次调用 create。

必须先 `list` + operation/status 对账。

如果历史已经清理、而平台无法证明原 create 是否产生过仍需处理的实例：

> 保持资源/业务为 unknown 或进入 quarantined，等待明确人工处理；不得用一个新 key 猜测性重开。

# 27. 网络失败与安全重新调度

浏览器请求超时：

```text
结果未知
```

客户端刷新后查询当前 owner 的活动 ServerRequest，不直接创建新申请。

Node stale/offline：

- 停止向该 Node 新建 Allocation / NodeJob；
- Existing Allocation 不释放；
- 不自动在其他节点复制服务器。

NodeJob 如果可能已经 create：

- 不自动改派；
- 先恢复联系和对账；
- 只有确认没有产生副作用才允许结束当前 Allocation attempt。

## 27.1 Allocation attempt

一个 ServerRequest 可以按顺序产生多个 Allocation attempt：

```text
ServerRequest S
├─ Allocation #1 → Node A
└─ Allocation #2 → Node B
```

但：

- 任意时刻最多一个 attempt 拥有当前调度权；
- Allocation 创建后 `node_id` 不原地改写；
- create side effect unknown 时绝不创建第二个 attempt；
- 只有旧 attempt 已 `released_no_effect` 或其他明确不占资源的安全终态后，才能重新调度；
- 新 attempt 创建时重新读取当时的 ArcadeGame `current_content_version_id` 并冻结自己的 `content_version_id`。

如果旧 Allocation 进入 quarantined，玩家“放弃异常服务器并继续”不是把原 ServerRequest 改派：

> 旧记录保留并解除 owner 阻塞，随后创建一个新的 ServerRequest。

# 28. 玩家状态

| 玩家显示 | 内部含义 |
|---|---|
| 未申请 | 无 blocking 活动申请 |
| 等待服务器 | `ServerRequest waiting`，尚无 Allocation |
| 正在分配 | 已创建/预留 Allocation |
| 正在启动 | `creating` |
| 可以进入 | d2core `active/running/ready` 且有效 JoinInfo 已生成 |
| 连接信息不可用 | d2core 已 Ready，但 Controller 无法为实际端口生成可靠公网 JoinInfo |
| 正在结束 | `stopping` |
| 已结束 | Allocation 已 `reclaimed` |
| 申请已取消 | 纯 waiting 阶段安全取消 |
| 内容已下架/不可用 | waiting 请求因 ArcadeGame/GamePreset `enabled=false` 被终结 |
| 启动失败 | create/启动失败且当前不再自动重试 |
| 节点暂不可达 | stale/offline |
| 状态暂时无法确认 | NodeJob/Allocation 等待对账 |
| 服务器清理异常 | `quarantined` |

`Ready != 真人已进入`。

`d2core Ready` 也不自动等于“玩家可进入”：

> 还必须能够根据该实例实际本地端口生成可靠 JoinInfo，才设置 `join_info_available_at` 并显示正式进房入口。

# 29. 手动结束与下一局

只有队长可结束。

正常结束：

```text
队长结束
→ NodeJob stop
→ d2core stop
→ operation terminal
→ status
→ 完整 reclaim
→ Allocation 结束
→ 释放容量
```

## 29.1 下一局不是 restart

“下一局”不是 d2core restart。

队长点击“下一局”时，平台持久化一个 next-game intent，并立即进入当前实例正常结束流程：

```text
记录 next-game intent
→ stop 当前 Allocation
→ 完整 reclaim
→ 创建新的 ServerRequest
→ 正常 FIFO
```

新 ServerRequest 默认继承：

- ArcadeGame；
- GamePreset；
- auto/manual 节点选择方式；
- 如果是 manual，继承原选 Node。

但：

- 不继承队列优先级；
- 新 ServerRequest 的 `requested_at` 是**完整 reclaim 后真正创建新请求的时间**；
- 新 Allocation 使用届时 `ArcadeGame.current_content_version_id`；
- 不调用 d2core 实例 `restart`。

如果 stop/reclaim 失败并进入 quarantined：

- 不自动创建下一局 ServerRequest；
- next-game intent 保持暂停；
- 队长必须先选择“放弃此异常服务器并继续”；
- 该动作解除旧资源的业务阻塞后，才消费 next-game intent 创建新 ServerRequest。

如果队长只是选择普通“结束服务器”而不是“下一局”，则完整 reclaim 后不自动创建新申请。

# 30. 异常隔离（quarantined）与玩家脱困

适用于：

- stop 明确失败；
- identity/status 无法可信确认；
- cleanup 明确失败；
- Node 在存在可能副作用的 Allocation 时长期失联；
- 其他底层是否释放无法判断的情况。

隔离资源：

- 继续占节点容量；
- 原端口不能视为空闲；
- 保留诊断；
- 等管理员后续处理。

## 30.1 进入 quarantined 的规则

以下情况可立即进入：

- stop / cleanup 明确失败且自动重试无法安全收敛；
- d2core 明确报告无法确认/恢复实例身份；
- 管理员依据诊断手动标记。

对于“Node 不可达但不知道实例是否仍存在”的 unknown：

```text
PlatformSettings.quarantine_after_node_unreachable
```

作为自动脱困阈值，V1 默认：

```text
15 minutes
```

部署方可以调整。

阈值到达后：

- Allocation 进入 quarantined；
- 仍然**不释放**旧容量；
- 不宣称旧服务器已经停止；
- 只是允许业务 owner 脱离异常资源。

管理员可以在阈值前手动进入 quarantined，也可以继续等待节点恢复。

## 30.2 玩家脱困

当 Allocation 已明确进入 quarantined 后，队长可执行：

> **放弃此异常服务器并继续**

该动作：

- 二次确认；
- 解除旧 ServerRequest 对 Party/User owner 的 blocking 状态；
- 保留旧 ServerRequest / Allocation / NodeJob / instance 关联；
- 不释放旧节点容量；
- 不宣称旧服务器已经停止；
- owner 可以创建新的 ServerRequest；
- 如果存在暂停的 next-game intent，则按 §29 创建新 ServerRequest。

管理员后续清理旧资源时，如果最终确认完整 reclaim，才真正释放该节点容量。

# 44. 性能与玩家体验指标

“玩家多久拿到可用进房方式”是 V1 的正式体验指标。

## 44.1 指标定义

定义：

> **可进房时间（Time to Join Ready）**：从玩家提交开服申请，到网页首次可以向玩家提供并启用实际可用的进房方式所经过的时间。

这里的“进房方式可用”至少要求对应实例已经达到：

```text
lifecycle = active
process = running
room = ready
```

不能因为 IP/端口已经提前分配，就提前把仍未 Ready 的服务器显示成“可以进入”。

## 44.2 时间拆分

每次 ServerRequest / Allocation 至少记录以下时间点：

```text
requested_at
assigned_at
create_started_at
ready_at
join_info_available_at
```

可计算：

```text
queue_wait
= assigned_at - requested_at

dispatch_and_start_delay
= create_started_at - assigned_at

dota_startup_time
= ready_at - create_started_at

time_to_join
= join_info_available_at - requested_at
```

如果某些阶段没有发生，对应字段允许为空，但不得伪造时间。

V1 的上述五个用户体验时间点统一使用 **Platform Server 的 UTC 时钟**：

- `requested_at`：Platform 接收并提交 ServerRequest 的时刻；
- `assigned_at`：Platform 成功创建/提交 Allocation 预留的时刻；
- `create_started_at`：Platform 收到 Controller 已开始执行该冻结 NodeJob 的确认时刻；
- `ready_at`：Platform 收到该实例达到 d2core Ready 的可信上报时刻；
- `join_info_available_at`：Platform 首次同时拥有 Ready + 有效 JoinInfo 的时刻。

浏览器轮询命中时间不作为 `join_info_available_at`，避免把前端轮询间隔随机混入 P50/P95。

Controller 可以额外上报本机诊断 duration，但跨组件的正式用户体验指标不直接相减不同机器的 wall clock。

## 44.3 无排队与有排队必须分开

### 有可用容量

当节点已有容量时，Platform / Controller 自身调度延迟应保持秒级，主要耗时通常来自 Dota 实际启动到 Ready。

具体秒数不能在开工前凭经验写死。

P1 真实联调后，应按至少以下维度建立启动基线：

```text
Node
OS
ArcadeGame
GamePreset
```

正式上线前，再根据真实样本决定是否需要为**无排队场景**下的 `dota_startup_time` / `time_to_join` 定义 P50、P95 等体验目标。

排队等待 `queue_wait` 单独统计，不计入“启动性能”P50/P95 或对应 SLO；否则前序房间正常占用资源会把队列等待误算成平台/游戏启动性能问题。

### 正在排队

如果没有可用节点容量：

> `time_to_join` 会包含前序玩家释放资源的等待时间，因此不能可靠预测一个精确 ETA。

V1 可以显示：

- 正在等待服务器资源；
- 前方队伍数量（如果能够准确计算）；
- 当前选择的是自动节点还是指定节点。

V1 不应向玩家显示没有可靠依据的“预计 X 分钟后开服”。

## 44.4 玩家页面行为

实例仍在启动时：

```text
正在启动服务器……
```

即使此时已经知道 host/port，也不启用正式进房按钮。

达到 Ready 后才启用：

- Steam 一键进入（当前配置 verified + enabled 时）；
- 蒸汽平台一键进入（当前配置 verified + enabled 时）；
- `connect` 兜底。

## 44.5 管理员可观测性

管理员至少能够查看或通过结构化数据获得：

- 最近启动耗时；
- `dota_startup_time`；
- `time_to_join`；
- 成功/失败结果。

在有足够的**无排队启动样本**后，可以增加：

```text
P50
P95
```

并按 Node / OS / ArcadeGame / GamePreset 比较。

该数据用于发现：

- Dota 更新后启动明显变慢；
- 某个 GamePreset 特别慢；
- 某节点/某操作系统异常。

## 44.6 V1 当前性能目标

V1 不预设固定的“必须 N 秒内 Ready”数值。

正式要求是：

1. 从 P1 开始记录上述时间点；
2. 区分排队等待和实际启动耗时；
3. 不让平台自身产生明显、无理由的长延迟；
4. 在真实环境建立基线；
5. 正式上线前基于无排队真实样本决定是否写入数值型启动 SLO；排队等待保持独立指标。

# 45. 上线前关键验收

| 场景 | 必须结果 |
|---|---|
| 连续点击/重复 POST | 同一 owner 返回原 blocking ServerRequest，不重复建申请或服务器 |
| 查询当前活动申请 | 浏览器响应丢失后可恢复原 ServerRequest |
| 无排队开服 | 记录申请→分配→create→Ready→进房信息可用的完整时间点 |
| Dota 启动耗时 | 能与排队等待时间分开统计 |
| 有排队 | 不显示无可靠依据的精确 ETA |
| 未 Ready | 即使已知道 host/port，也不提前启用正式进房入口 |
| Controller 在首次 create 前崩溃 | frozen execution record 未提交则不调用 core；恢复后安全继续 |
| create 结果未知 | 同一 node_job_id → 同一 idempotencyKey + 同一冻结参数，对账，不重复 create |
| create 明确无副作用拒绝 | Allocation released_no_effect，安全释放预留 |
| create 已受理后失败 | failed_unreclaimed → stop/reclaim；未回收不释放 |
| 两队争最后名额 | 事务/锁下只有一个 Allocation 预留成功 |
| 安全取消 | 只有纯 waiting 且无 Allocation 的请求可立即取消 |
| 安全重调度 | 旧 Allocation node_id 不改写；确认无副作用后创建新 attempt |
| hard/desired max | desired 不超过 hard；occupied 达 min(hard,desired) 后不再调度 |
| NodeJob 可能已有副作用 | 不自动改派 |
| Web/Controller 重启 | 状态恢复且不重复 create |
| Node 断联 | Existing Allocation 不释放 |
| 普通队员伪造 stop | 拒绝 |
| stop/cleanup 明确失败 | quarantined |
| Node 带有可能副作用的 Allocation 失联超过默认 15 分钟 | 可自动 quarantined，但旧资源仍占容量 |
| quarantined 玩家脱困 | 可重新申请，旧资源仍占容量 |
| 正常结束 | 完整 reclaim 后才释放 |
| 下一局 | next-game intent 持久化；先回收再创建新申请；新 requested_at 不抢队列优先级；不调用 restart |
| connect | IP/域名和实际公网端口可用；Ready 页面可复制命令 |
| connect 手动帮助 | 玩家仅依赖网页帮助即可知道如何启用/打开控制台并执行平台生成的 connect 命令 |
| A2S 可查但 URI 不可进 | 不标 entry verified |
| 无 Ready 实例或瞬时 A2S 查询失败 | 分别表示尚无查询事实或该实例失败；不改变真人验证、关闭按钮或影响 connect；玩家侧不暴露 A2S |
| entry 未 verified | 不允许 enabled |
| 当前入口配置真人验证 | 管理员二次确认对应 scheme 的真实 URI 曾成功进入真实 Ready 实例；无需逐端口覆盖 |
| 同一入口配置修订 | verified 只能由管理员确认变 true；入口异常时关闭 enabled，不提供普通撤销验证 |
| 多个 Ready 实例 | 后台分别显示每个实例的 A2S 结果与检查时间，不能只显示节点聚合布尔值 |
| 网络配置变化 | verified/enabled 自动失效 |
| 厂商 NAT | connect_host 域名 + explicit mapping 可工作 |
| 实例实际端口无公网 mapping | 不生成猜测 JoinInfo，不标记可进入，结构化报错 |
| 非对称 NAT | connect 可用，一键入口独立真人验收 |
| 浏览器冷启动问题 | 始终有 Steam/Win+R/connect 兜底提示 |
| 全局维护 | 网站/队伍/已有实例继续可用，所有新申请与 waiting 调度暂停 |
| 内容维护 | 只暂停对应 ArcadeGame/GamePreset，新申请与 waiting 调度暂停，其他内容正常 |
| 维护开关 | 不自动停止已 dispatched/creating/running 的实例 |
| Node Drain | 存量继续、新 Allocation 不进入该节点 |
| Node × ArcadeGame 排空 | 只暂停该节点该游戏的新 Allocation，不影响其他游戏 |
| 公告 | 玩家页面能看到全局或内容维护原因 |
| Content Tool | 不自行 Drain、不下载地图、不把目录链接当活动实例热切换机制 |
| 单节点 ContentVersion 更新 | 内容维护/Binding 排空 → switch → Controller readback → Node Drain 本地验证 → current version 发布 |
| 双节点 ContentVersion 更新 | current version 切换前后调度闭合；旧局继续，新 Allocation 只进入 reported 新版节点 |
| NodeContentBinding | reported version 只能由 Controller 节点事实上报；Platform 仅控制 accepting；版本不匹配不调度 |
| 内容验证实例 | 仅在 Node Drain 维护窗口本地手工创建；完整 stop/reclaim + resync 后才 Resume |
| Allocation ContentVersion | 每个 attempt 创建时从 ArcadeGame.current_content_version_id 快照，之后固定 |
| d2core/Dota 更新 | 人工 Drain 后更新 |
| 原始日志 | 不持续上传 Web |

# 46. 真实环境参数与阶段授权原则

真实服务器 IP、域名、SSH 信息、Dota 安装路径、数据库位置、NAT 映射、凭据等属于**具体部署环境参数**，不写入公开正式任务书。

本规格只定义“某个阶段需要哪类信息”，不保存项目所有者当前机器的实际值。

执行规则：

- P-1 UI 原型不需要任何真实服务器信息；
- 进入需要真实环境的 P0/P1/P3/P5 子阶段前，开发 Agent 应根据该子阶段列出**本次实际需要的最小输入**；
- 等待项目所有者在当前会话中明确提供并授权；
- 不得从历史聊天、示例配置、旧部署记录、已有 SSH 权限或其他节点信息推断本轮授权；
- 不得因为“已经有连接权限”而默认允许修改生产环境；
- Secret、密码、私钥等只通过当前安全部署方式提供，不写入任务书、Git 或公开文档。

```text

OS / d2core install/bin / data-dir / Dota root /
端口池与 d2core service 参数 / connect_host / protocol_ip /
```

以上只是输入**类别**，不是本项目实际部署值。

- V1 以节点作为内容版本隔离边界；单节点可 Drain 更新，多节点可滚动发布；
- 内容更新有明确低风险流程；
- Content Tool 降低正常 VPK 更新的人工错误；
- V1 成功不依赖活动实例热切 VPK；
- 即使项目后续长期停止开发，V1 本身也应能够长期解决自助专服的核心需求。

6. 如果未来必须改变已经冻结的数据不变量、状态语义、组件职责或 V1 产品范围，应显式修订规格版本，不得只在实现代码中静默改变。

> **当前结论：V1 规格审查阶段结束；下一阶段为 P-1 UI / UX 原型。**

# 附录 A：V1 交付与正式发布流程（维护者）

本附录供项目所有者/维护者组织 P0–P5 完成后的审查、候选验证、生产上线与正式发布。

> **本附录不是普通开发 Agent 的一次性执行授权。** 开发 Agent 不应因为读到本附录就自行发起独立审查、连接生产环境、创建正式 Tag/Release 或连续执行到 V1 发布。每一步由项目所有者另行明确发起；独立审查应由与开发过程相互独立的审查会话完成。

P0–P5 功能开发完成不等于直接上线。维护者后续按以下闭环组织交付。

## A.1 集成候选冻结

- 完成 P0–P5 阶段验收；
- 跑完整自动测试；
- 完成双平台 Node Controller 验证；
- 完成至少一个真实 Dota 端到端闭环；
- 固定候选完整 commit SHA；
- 候选冻结后不边审边继续开发新功能。

## A.2 独立代码审查

由项目所有者另行发起多个互相独立的审查会话，对同一固定 SHA 审查：

- 状态机与竞态；
- 重复开服/误释放资源；
- 授权与越权；
- Node/Controller/Web 重启恢复；
- NAT/A2S/entry 语义；
- ContentVersion/NodeContentBinding；
- 管理员安全；
- 数据库迁移；
- Windows/Linux 差异。

独立审查不直接修改代码。

## A.3 汇总裁决

对所有审查报告：

- 去重；
- 核对实际固定 SHA；
- 对争议项做源码检查或隔离复现；
- 区分确认问题、误报、未验证项；
- 形成一份统一修复任务单。

不以简单多数票代替裁决。

## A.4 定向修复与回归

只修已裁决问题。

每项修复：

- 有对应回归测试；
- 不顺手扩大功能；
- 必要时做真实 Dota/双平台专项复验。

## A.5 RC1 工程候选

检查：

- test/vet/build；
- Windows/Linux CI；
- 数据库 migration；
- Web/Controller restart；
- 安装/升级/回滚；
- 开源仓库卫生；
- README/部署/运维文档；
- Release 打包。

## A.6 RC2 真实环境烟测

至少覆盖：

```text
网页申请
→ 调度
→ d2core create
→ Ready
→ 一键入口 / connect
→ 真人进房
→ 下一局 / 结束
→ stop/reclaim
```

以及：

- 多人 Party；
- 多节点；
- Windows/Linux Controller；
- Node 断联/恢复；
- quarantined 玩家脱困；
- 全局/内容/节点维护；
- A2S/Steam/steamchina；
- NAT；
- ContentVersion 单节点更新；
- 若有双节点，做一次滚动内容发布；
- 备份/恢复演练。

## A.7 小范围生产上线

- 先部署 Web 控制面；
- 先接入明确授权的新/测试游戏节点；
- 小范围真实玩家试用；
- 观察错误率、启动耗时、资源回收和数据库状态；
- 已在提供服务的旧生产节点最后再按明确授权决定是否加入。

## A.8 V1 正式发布

固定最终：

- Git tag；
- 完整 commit SHA；
- Platform Server / Node Controller / Content Tool 正式构建；
- SHA256；
- migration 版本；
- Node API 版本；
- Release Notes；
- 部署文档；
- 升级/回滚文档；
- 已知限制；
- 固定 d2core 依赖的许可证/再分发状态与最终 Release 打包方式已再次确认。

发布后停止继续向 V1 塞新功能。

后续功能另起版本阶段。
