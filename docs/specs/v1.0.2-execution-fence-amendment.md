# v1.0.2 execution-fence Owner amendment

Status: **Owner-approved frozen amendment for I2**. This document is authoritative for the execution-fence language in [v1.0.2 content maintenance and validation](v1.0.2-content-maintenance-validation.md), §§12–13. It does not change `docs/specs/v1.md` or authorize I3, deployment, or a d2core change.

## Decision and reason

The original I2 candidate `7edaa6a41a38c5f53c0c9962e498c40ef86084c5` was **HOLD** after independent Reviewer B deterministically reproduced both replacement-after-check and expiry-after-check. The old claim that a completed session replacement or expiry prevents every later local `Core.Create` or `Core.Stop` side effect is withdrawn. A `/session/check` response ends before the local call; another check only moves that gap. The Platform cannot atomically revoke a paused process's access to unchanged d2core across the network without a local authoritative executor or d2core fencing token. Neither is part of V1.

The Owner adopts the following narrower safety contract together with two mandatory implementation measures: a durable operation-start linearization point and an OS-level node-local exclusive Controller lock. This is a contract change with code remediation, not an accepted unaccounted side effect.

## Frozen execution boundaries

1. **Platform work and payload.** Every v1.0.2 Job/Allocation request is checked against the current Node capability session. Replacement or expiry denies the old session new open/claim/GET/prepare/report, active Allocation reads, instance facts, inventory, and new operation-start. The request fence serializes completed HTTP requests with session replacement; it does not extend through local d2core calls.
2. **Operation start.** Before each v1.0.2 `Core.Create` or formal `Core.Stop`, the Controller must submit the exact Job, kind, and frozen create request or stop instance to the session-fenced Node API. In one database transaction the Platform verifies the immutable identity and durably moves the Job to `unknown` / **MAY-HAVE-STARTED**, with Allocation/resource accounting updated. This commit is the execution linearization point. Only a successful response confirming that durable state permits the local call. A failed, denied, or lost response permits no local call by that Controller attempt. `unknown` re-entry for the same identity is idempotent. Node API path and `APIVersion=1` remain wire-additive.
3. **Already authorized in-flight operation.** After that commit, a paused Controller may make the exact local call after session replacement, lease expiry, or Platform restart. This call belongs to the already authorized operation. The Platform must retain `unknown`/may-have-effect accounting through crash, response loss, and recovery. It must not report `rejected_no_effect`, release capacity, reassign, create another Job/key, or claim no effect solely because the call may not have happened. A new capable Controller uses the same Job, frozen path/port/fingerprint and deterministic d2core idempotency key, or the same formal stop Job/instance, to retry or reconcile. Create retry still obeys fixed d2core history bounds; uncertainty past that bound remains fail closed. Only trusted core operation/status and full `reclaimed/stopped/complete` facts can establish the relevant resource outcome.

The same rule applies if the Controller crashes **after** the durable commit and **before** the first core call: zero observed core calls are not sufficient to release the reservation. A clearly proven pre-marker mismatch can still be rejected with no effect. A core rejection after the marker is `unknown` for this purpose.

## Node-local ownership

Each new official Controller acquires an OS exclusive lock before obtaining a capability session and holds its handle for the entire process lifetime. A second new Controller for the same Node on that host fails closed before the Runner. Windows uses `LockFileEx`; Linux uses `flock`; process exit or handle close releases the lock. The Node-specific absolute lock file is derived from the local parent of the configured d2core data directory, which must be an operator-controlled, non-public directory; it is outside Git and cannot be selected by an Admin/Web request. On Linux a world-writable parent is rejected. Node host operator and Node Secret holder are trusted node principals; the lock handles duplicate supervisors and restart overlap, not a malicious custom client.

Old binaries do not acquire this lock, so rollout remains **stop old Controller → confirm exit → start new Controller**. An old binary may continue legacy_v1 work during compatibility windows but cannot obtain v1.0.2 payload or capability session automatically. Heartbeat capability is a reported machine fact; capability session is Platform request authorization. This version does not add binary attestation or a separate capability credential.

## Scope and migration

Existing durable `node_jobs.state=unknown` and Allocation unknown/stopping accounting represent MAY-HAVE-STARTED without a new column or migration 0022. No d2core change, new local broker, arbitrary execution endpoint, or Node API version bump is authorized. The original independent review finding and earlier candidate remain historical facts; this amendment governs the remediated candidate.
