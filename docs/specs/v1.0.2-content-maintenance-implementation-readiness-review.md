## 2. Executive result

**HOLD.** BLOCKER: **0**; HIGH: **2**; MEDIUM: **1**; LOW: **0**. The three Owner directions are present, and the proposed data model can be migrated forward. Two safety contracts need narrow edits before Implementation Phase: fencing an old Controller from an already-frozen new Job, and resolving the actual `ServerRequest`/`Allocation` reverse lock order. This is not a request to reopen product design.

## 3. Owner adjudication implementation check

1. **Node × ArcadeGame scoped maintenance — implemented in the candidate.** §§7, 11, 14 and 15 drain only the target game's allocations while retaining all games in node capacity. Other games' jobs and instances continue.
2. **Minimum Controller/Node API v1 additions — implemented in direction, incomplete in upgrade fencing.** §§8, 9 and 12 add machine template facts, capabilities, full inventory and pre-create checks without changing d2core. Finding H-01 concerns a resumed frozen Job, not the decision to add machine proof.
3. **Per-Preset validation/publication — implemented.** §§3 and 10 require a distinct PASS for each opened preset and pause uncovered presets on first v1.0.2/content-pointer publication. §3 correctly notes that starting another maintenance epoch on the same node invalidates its earlier PASS, so a second preset may require revalidation there.

## 4. Data model review

`ValidationRun` fixes node, game, preset, content, template, fingerprint, epoch and fact revisions (§4). `Allocation.purpose` and owner XOR (§5) preserve the distinction between Request, Allocation, Job and core instance; a validation Allocation has no player Request and one create Job. The existing schema has a non-null `server_request_id`, immutable identity trigger, unique create/open-stop indexes and `integration_only=(allocation_id IS NULL)` ([0005](../../internal/platform/store/migrations/0005_p1b_allocations.sql)); all can be changed forward with new constraints and a validation branch in reporting. The candidate explicitly requires that branch (§§16, 21). The release tables and monotonic fact/epoch counters are additions, not historical rewrites. The proposed final-fact comparison is feasible under the node lock, although the current heartbeat temporarily resets all bindings to `unknown` before upsert ([nodes.go](../../internal/platform/store/nodes.go#L138-L178)); revision increments must use the prior and final facts, as §16 says.

## 5. Lifecycle safety review

The candidate distinguishes `create_pending`, observing/unknown, Ready without JoinInfo, awaiting human, cleanup/stop, quarantine and final pass/fail (§6). A human pass is only an audited claim; final PASS additionally needs current machine facts, trusted create identity, Ready, valid JoinInfo, a formal stop Job, terminal stop reconciliation, `reclaimed/stopped/complete`, and no unresolved Job. Human fail still goes through cleanup. Unknown create cannot be released by an empty list or later rejection (§§6, 19), matching the current FIX-05 guard in [node_jobs_api.go](../../internal/platform/store/node_jobs_api.go#L191-L199). A failed effectful create with a trusted ID can use the current automatic stop pattern; an unknown create without an ID remains occupied/quarantined. The fixed key and frozen request follow [jobs.go](../../internal/platform/store/jobs.go#L62-L97); core create still takes only key/path/port ([core/client.go](../../internal/controller/core/client.go#L85-L100)). No second create or unsafe no-effect release is authorized by the candidate.

## 6. Capacity review

Both purposes use the existing `occupied` predicate, which counts every Allocation except `reclaimed` and `released_no_effect` ([node_eligibility.go](../../internal/platform/store/node_eligibility.go#L47-L57), [capacity.go](../../internal/platform/store/capacity.go#L18-L26)). §5 requires player and validation reserve to lock the same Node row and recheck that count, so only one can take the final slot. Unknown, failed-unreclaimed and quarantined remain occupied; stale/offline does not release them. `integration_only` is expressly barred for validation. This is implementable but needs the specified PostgreSQL race test.

## 7. Scoped maintenance review

The close/reserve serialization in §15 addresses the current scheduler's Node lock followed by an unlocked binding/capacity read ([allocation.go](../../internal/platform/store/allocation.go#L75-L154), [node_eligibility.go](../../internal/platform/store/node_eligibility.go#L47-L57)). The candidate requires binding/template rechecks under locks and an epoch gate. Its drain excludes other games' accounted allocations, while counting them for capacity; any unaccounted core instance fails the node proof closed. It does not order stops for existing players or rewrite their snapshots. A switch remains a manual Content Tool operation after the target game has drained.

## 8. Template identity/readiness review

The proposed `template-manifest-sha256-v1` includes the template's raw bytes/path and declared external dependency paths, lengths and digests (§8). Thus template JSON covers `arguments`, `cfg.lines` and readiness, while the manifest does **not** claim automatic discovery of arbitrary `exec`/cfg references. Unsupported or mutable dependencies are unknown and cannot pass. The Controller resolves the local binding key, checks candidate content SHA and manifest before first core create, and records the observed fingerprint with the existing frozen key/path/port. Fixed d2core is never asked to understand the new fields. The last-check-to-core-open file race remains subject to the stated immutable directory/permissions discipline; real-node validation is still necessary.

## 9. Inventory/unaccounted review

§9 requires an authenticated complete `list` report, unique scan ID, server receipt time, matching heartbeat state, and Platform-side reconciliation to nonterminal Allocation/create-Job identity. `complete=false`, missing/truncated/duplicate data, stale facts, and failed delivery cannot become an empty proof. Integration-only and terminal-allocation active instances are unaccounted. The present adapter's [List](../../internal/controller/core/client.go#L141-L150) normalizes a nil `instances` slice to empty; implementation must distinguish missing/null from an actual complete empty list before setting `complete=true`, as the candidate already requires. A same-node inventory/heartbeat lock and new scan on every attempt make the fail-closed rule implementable.

## 10. Publish/rollback review

The specified `release.publish` locks game/presets, checks expected-old content/template/accepting state, requires a current PASS per opened preset, pauses unproved presets and atomically writes immutable release/Audit records (§10). First v1.0.2 publication upgrades all of a game's presets; a content pointer change enumerates all presets. Waiting Requests read the current pair only when allocating; old Allocation snapshots stay fixed. Rollback (§14) is a new release after restoring old bytes and template fact and obtaining new epoch-specific Runs; old PASS is not reused. These rules prevent an unplanned `v2+t1` admission or unproved preset reopen **if every pointer-writing Admin route obeys them**. Finding M-01 requests an explicit disposition for the existing `content.publish` route.

## 11. Concurrency / lock review

Current scheduler order is advisory scheduler lock → waiting `ServerRequest` → shared Settings/Game/Preset → exclusive Node → eligibility read → new Allocation/Job ([allocation.go](../../internal/platform/store/allocation.go#L23-L60), [allocation.go](../../internal/platform/store/allocation.go#L75-L154)). Current heartbeat takes Node, then updates content bindings ([nodes.go](../../internal/platform/store/nodes.go#L132-L178)). Admin `content.publish` takes Game, then shared Node/Binding ([admin_actions.go](../../internal/platform/store/admin_actions.go#L185-L209)); `binding.update` and `template_binding.upsert` currently lock only their binding rows and must acquire Node first as §15 states. The candidate's public-object order is implementable for scheduler, heartbeat, binding changes and new publish if all handlers use it.

The existing **report/admin path is different**: `ReportJob` locks Job → Allocation → updates ServerRequest ([node_jobs_api.go](../../internal/platform/store/node_jobs_api.go#L153-L156), [node_jobs_api.go](../../internal/platform/store/node_jobs_api.go#L247-L251), [node_jobs_api.go](../../internal/platform/store/node_jobs_api.go#L315-L346)); `ReportInstanceFact` locks Allocation → updates ServerRequest ([reconcile.go](../../internal/platform/store/reconcile.go#L59-L63), [reconcile.go](../../internal/platform/store/reconcile.go#L102-L130)); `request.stop` locks ServerRequest → Allocation ([admin_actions.go](../../internal/platform/store/admin_actions.go#L416-L429)). For a running request, concurrent `request.stop` and an active-instance fact that quarantines it can each hold one row and wait for the other. §15's phrase that reports retain the existing Job→Allocation *local* order does not resolve the Request edge. H-02 gives the necessary correction. No live PostgreSQL schedule was run.

## 12. Migration review

**Forward migration is feasible without editing migrations 0001–0019 or changing existing production rows' meaning.** `server_request_id` must become nullable only for validation, with a purpose/owner XOR and a validation FK; existing rows backfill to player. The allocation trigger must add `purpose`/`validation_run_id` and continue protecting node/game/content/template/attempt identity; existing player uniqueness and blocking-request indexes stay effective ([0004](../../internal/platform/store/migrations/0004_p1a_catalog_requests.sql#L68-L85), [0005](../../internal/platform/store/migrations/0005_p1b_allocations.sql#L30-L84)). The Job business-owner CHECK remains unchanged. `node_content_bindings` and `node_template_bindings` can gain epoch/revision and generation/expected fingerprint columns; Controller facts and inventory need separate reported tables. `game_presets` can backfill `legacy_v1`; the historical [content_release_validations](../../internal/platform/store/migrations/0014_p5a_content_publication.sql) cannot be promoted into Run PASS. New release/history tables are additive. [ApplyMigrations](../../internal/platform/store/migrations.go#L66-L127) checks old checksums and applies new numbered SQL transactionally. SQL execution and index/trigger behavior on a migrated disposable database were not verified.

## 13. Node API / Controller compatibility

`APIVersion=1` and the d2core constants are fixed in [nodev1 types](../../internal/contracts/nodev1/types.go#L16-L24). New request fields require Platform deployment before new Controller because the current Node HTTP decoder rejects unknown fields ([node.go](../../internal/platform/httpapi/node.go#L36-L49)). Legacy heartbeat/job shapes can remain valid; old Controllers can continue normal v1.0.1 create, stop and reconciliation while their node/preset remains legacy. New Controllers can keep the pinned core client. **The claimed mixed-version safety for new Jobs is incomplete:** old response decoding ignores added fields, and `/jobs/open`/claim currently authenticate only the shared Node credential; the old runner can execute a returned frozen Job without `/prepare` ([runner.go](../../internal/controller/runner/runner.go#L188-L223)). See H-01. Upgrading all Controllers eventually does not fix an old process or rollback that resumes an already-prepared Job.

## 14. d2core / Content Tool impact

No d2core change is required by the proposed contract: the pinned client adapter already exposes create, operation, status, list and stop; its status fields support Ready/JoinInfo processing and the reclaim triple ([core/client.go](../../internal/controller/core/client.go#L35-L75), [runner.go](../../internal/controller/runner/runner.go#L449-L451)). No fingerprint, manifest, arbitrary console, per-instance VPK mount or new core protocol field is proposed. Existing Content Tool entry points are `status`, `prepare`, `switch`, `rollback` ([main.go](../../cmd/content-tool/main.go#L32-L55)); §11 keeps their invocation local and explicit. Live behavior was not tested in this review.

## 15. Backward compatibility

A new Platform with forward-migrated DB can preserve old player rows and legacy preset scheduling, and an old Controller's existing v1.0.1 heartbeat/Job requests can remain accepted. The new Controller can use fixed old d2core. Existing content versions and historical validation rows retain their meanings. During a rolling Controller upgrade, normal player create/reclaim can continue on legacy combinations **provided** new Platform preserves old wire shapes, does not globally require new capabilities for legacy Jobs, and keeps those routes operational. Admission for `v1_0_2` presets correctly requires new Controller facts. H-01 is the exception that prevents declaring the new-Job mixed-version rollout safe as written.

## 16. Findings

### H-01

- **ID:** H-01
- **Severity:** HIGH
- **Spec section:** §§12–13, 20 (capability gate, additive upgrade, Controller recovery).
- **Code evidence:** [node.go](../../internal/platform/httpapi/node.go#L138-L169) serves `/jobs/open` and claim using only Node authentication; [nodev1.Job](../../internal/contracts/nodev1/types.go#L78-L91) is ordinary JSON; [runner.go](../../internal/controller/runner/runner.go#L188-L223) skips `/prepare` when `FrozenCreate` is already present, then calls core `Create`. The current [OpenJobsForNode](../../internal/platform/store/node_jobs_api.go#L73-L95) returns all open Jobs for that Node. Both Controller versions use the same Node credential.
- **Problem:** A heartbeat capability is a **node's last report**, not proof that the process making a later `/jobs/open` request understands new expected fields. If a new Controller prepares a v1.0.2 Job and crashes or is rolled back, an old Controller can read that claimed/unknown Job, ignore added JSON fields, and execute the frozen core request without the new template/content check. A simple claim-time capability filter or `/prepare` rejection does not fence this recovery path.
- **Impact:** Side-effectful create of unverified content/template under the v1.0.2 validation identity; mixed-version upgrade/recovery is not safe by the claimed additive contract.
- **Required change:** Specify a per-request/per-process v1.0.2 capability proof or equivalent version-fenced job lease for **claim, open-job recovery, get, prepare and execution**. New Jobs/frozen executions must never be exposed for side-effect execution by a legacy client. Keep old clients able to process legacy Jobs. Add a new-prepared-Job → old-Controller recovery test; if v1 additive cannot fence this, require a protocol version bump before implementing new Jobs.

### H-02

- **ID:** H-02
- **Severity:** HIGH
- **Spec section:** §15 (global lock order and claim that Job→Allocation is a local report order).
- **Code evidence:** [ReportJob](../../internal/platform/store/node_jobs_api.go#L153-L156) then [applyAllocationJobReport](../../internal/platform/store/node_jobs_api.go#L247-L251) then Request update [L346](../../internal/platform/store/node_jobs_api.go#L346); [ReportInstanceFact](../../internal/platform/store/reconcile.go#L59-L63) then Request update [L130](../../internal/platform/store/reconcile.go#L130); Admin [request.stop](../../internal/platform/store/admin_actions.go#L416-L429) takes Request before Allocation.
- **Problem:** The stated public lock order places ServerRequest first but calls the existing report order merely Job→Allocation. In reality reports also write ServerRequest **after** Allocation. `request.stop` takes the opposite pair. For a running Allocation, a concurrent quarantining fact/report and admin stop can form `Request → wait Allocation → wait Request`.
- **Impact:** PostgreSQL deadlock and failed or delayed stop/reconciliation at a safety-critical state boundary. Retry may recover, but the spec explicitly requires no such deadlock and gives implementers an inconsistent order.
- **Required change:** Amend §15 to cover every transaction that writes ServerRequest, Allocation and Job. Establish and enforce one total order (for example, look up IDs without locking, lock player ServerRequest first, then Job/Allocation in a documented order, recheck identities; validation has no Request), or a proven equivalent split transaction. Update report/reconcile and admin paths together and require the PostgreSQL interleaving test for `request.stop` versus quarantining/reclaiming reports. Preserve atomic state and existing idempotency semantics.

### M-01

- **ID:** M-01
- **Severity:** MEDIUM
- **Spec section:** §§10, 16–17 (release pointer authority and legacy Admin routes).
- **Code evidence:** Current [content.publish](../../internal/platform/store/admin_actions.go#L185-L209) directly updates `arcade_games.current_content_version_id` using legacy `content_release_validations`; [content.validate](../../internal/platform/store/admin_actions.go#L157-L184) can update that historical table. Neither route has a ValidationRun or per-preset plan.
- **Problem:** The candidate says these rows remain legacy history and introduces `release.publish`, but does not explicitly name whether the old `content.publish`/`content.validate` actions are rejected, restricted to not-yet-upgraded games, or removed after a game's first v1.0.2 release. The broad no-bypass rule implies a guard, but the route transition should be explicit.
- **Impact:** Implementation could leave a legacy pointer-writing route callable on an upgraded game. The new scheduler proof gate should prevent unverified admission, but an accidental pointer shift could pause valid new allocations and omit release/Audit linkage.
- **Required change:** State that after a game enters `v1_0_2`, `content.publish` and `content.validate` cannot change its admission/pointers or create v1.0.2 proof; all future content/template pointer changes use `release.publish`. Preserve a deliberately bounded legacy path for not-yet-upgraded games if needed for rollout.

## 17. Required spec edits

1. Add H-01's request-bound Controller capability/fencing and recovery test to §§12–13/20, including already-frozen open Jobs. Explicitly retain legacy Job service for old Controllers.
2. Correct §15 per H-02 so report/reconcile and Admin `request.stop` share a provable Request/Job/Allocation order; require the concrete PostgreSQL deadlock interleaving test.

M-01 can be clarified during implementation without changing the core contract. No change to Owner's three adjudications, d2core, or Content Tool is requested.

**NO — H-01, H-02.** Do not freeze this wording or authorize I1 Schema + Store Implementation until those two narrow safety contracts are revised. Then recheck only the edits and their interaction with the existing invariants.
