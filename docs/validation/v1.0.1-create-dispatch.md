## Root cause and change

The former `Runner.Step` observed open jobs and returned without ordinary claim whenever any non-pending Job remained. Its only exception was `ClaimIndependentStop`. Thus a create operation in `accepted` or `unknown` could hold the entire Node's ordinary create dispatch until terminal, even though the Platform had reserved capacity for another Allocation.

Each Controller cycle now inventories d2core and durable open Jobs, then claims up to a bounded number of pending jobs. Existing and newly claimed Jobs run in a per-cycle worker group. One Job's operation or report error is returned for diagnosis but does not cancel another Job's execution. Workers join before the cycle returns; the next cycle or a restarted Controller reloads open Jobs from the Platform. The worker count is the configured `hard_max_instances`, clamped to 2–32. The minimum of two leaves a slot for an independent stop on a single-capacity node; Platform Allocation admission, not the worker count, enforces `min(hard_max_instances, desired_max_instances)` for new creates. At most one ordinary claim per worker slot is made in a cycle. The existing restricted independent-stop claim remains available.

The ordinary claim transaction now rejects a pending Job if another `claimed`, `accepted`, or `unknown` Job on the same Node has its Allocation ID or known instance ID. A Node row lock serializes concurrent claim transactions so two claimers cannot both pass this predicate before either commits. This small Store change is required because Controller memory alone cannot safely enforce the dependency across restarts or concurrent claims. No schema or wire-contract change is needed.

## Safety boundaries

| Boundary | Preserved mechanism |
| --- | --- |
| Create idempotency and frozen request | Existing immutable NodeJob ID derives the d2core key; `PrepareCreate` persists template, port and fingerprint before the core call. Each worker handles its own immutable Job snapshot. |
| Unknown / FIX-05 | Timeout and lost response retain `unknown`. This hotfix adds no no-effect proof, release, or reassignment. Old unknown work can occupy capacity indefinitely; quarantine and Owner escape remain available. |
| Identity | Claims exclude conflicting known instance and Allocation IDs. Existing report transactions reject changed instance/operation IDs and update only the Job's Allocation. |
| Restart | No long-lived worker state is authoritative. Open Jobs, frozen execution and core IDs are reloaded after restart, then observed or retried under the original key. |
| Stop / reclaim | Existing stop state machine and independent-stop route remain. Capacity still needs a clear no-effect rejection or `reclaimed/stopped/complete`; a failed operation by itself cannot release it. |
| Capacity | Scheduler reservations continue to guard the effective hard/desired limit. Worker slots limit simultaneous Controller API/core calls but never create a new Allocation. |

## Regression and isolated acceptance

Runner regressions cover overlapping independent core create calls, B claim/accepted while A is accepted, blocked A observation while B starts, slow A while B becomes Ready, unknown A with frozen-key retry while B proceeds, duplicate same-Allocation suppression, restart of two accepted Jobs with distinct IDs, create plus independent stop, separate full reclaim, one failed create beside a successful create, and a 20-Job bounded simulation with one observation error. Store regressions cover two claimed independent Allocations while capacity remains reserved, same-instance dependency exclusion, and racing claims of the same instance. The existing Controller, recovery, Store, scheduler, capacity and A.4 tests remain applicable.

For a separately authorized isolated real-node run, use the procedure in `docs/operations.md` under “Create dispatch hotfix acceptance.” The decisive timestamp assertion is that B's `create_started_at` precedes A's create Job terminal report. No Production test, Steam readiness change or d2core modification is part of this candidate.
