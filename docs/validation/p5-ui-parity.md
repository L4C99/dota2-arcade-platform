# P5 player/admin UI parity (implementation checked; final owner acceptance pending)

The player Ready panel renders only backend-provided, verified/enabled Steam and steamchina links. Manual `connect` remains available, with Steam-start, Win+R and Dota console help. The Admin page exposes multi-game/preset/version registration, Controller-reported bindings and digests, content validation/publication, A2S state and exact entry port coverage. The P5C URI flags remain false until the deferred real-client, per-port verification; the UI does not show one-click buttons prematurely.

The player page displays elapsed time while waiting and creating. Ready total uses the Platform's `join_info_available_at - requested_at`, to one decimal place; when present, queue wait and subsequent startup appear in details. No ETA, Controller claim delay, Steam login timing, d2core internals or P50/P95 are exposed to players. The original implementation passed typecheck, lint, seven Web tests and production build locally and in GitHub Actions [run 36246913436](https://github.com/L4C99/dota2-arcade-platform/actions/runs/36246913436), commit `40f9b1e875d3dc556be1db0cc1cb23ecaba1e42e`.

The exact `40f9b1e` Web bundle was installed on the development Web node from a clean build; HTTPS page and new JS asset returned 200. The actual development catalog showed both registered maps at 1440, 390 and 320 CSS pixels, with no horizontal overflow. Isolated browser-only API fixtures then exercised waiting, creating and Ready rendering at those widths: waiting showed `正在等待服务器 · 已等待 14 秒`; creating showed `正在启动服务器 · 已用时 28 秒`; Ready showed `服务器已就绪 · 本次开服用时 21.2 秒` and a separate queue/start detail. Waiting and creating exposed no JoinInfo; Ready exposed manual JoinInfo but no one-click URI because the flags are false. These fixtures changed browser responses only and did not create a server or establish a real player lifecycle.

The live Admin page was inspected in headless Edge at 1440, 390 and 320 CSS pixels, using a temporary development Admin account that was disabled after capture. Overview, content and node tabs rendered without API errors or mobile horizontal overflow. The content view presented the registration form, and the node view showed the Linux and Windows development nodes. This was visual and read-only page inspection; no Admin content or node action was submitted.

Final project-owner UI acceptance remains pending. The two-person player-flow trial and deferred URI checks are separate acceptance items; visual fixtures and one-person sessions do not satisfy them.

The owner later completed the live two-anonymous-session Party page flow (create, invite, both seeing two members, leave, disband) and reported normal operation. A separate one-person player Web request for new `custom` content reached Ready and JoinInfo, the owner reported joining and normal gameplay, and the server was fully reclaimed after the page stop. That trial exposed a timer regression: the waiting-to-creating transition reset the main counter to `create_started_at`, and the locally ticking counter could run past the formal Platform Ready time before the next poll displayed it.

The follow-up fix keeps the main pending counter on the same `requested_at` origin in every phase, shows the create-stage duration only as detail, and updates the pending counter to the server `Date` of the latest response that still confirmed pending. This prevents normal polling delay from making the pending display run beyond the Platform Ready timestamp; same-request observations are kept monotonic. The formal Ready total remains `join_info_available_at - requested_at`. Typecheck, lint, eight Web tests and production build passed locally for this fix. A fresh live owner recheck is still pending.
