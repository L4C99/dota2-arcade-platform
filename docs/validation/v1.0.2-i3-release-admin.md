This record covers the I3 implementation candidate only. The Production baseline remains v1.0.1. The work started from `origin/main` at `d4164e8a07dc4a5f2249a7a059e87bc86ef4e778` on `codex/v1.0.2-i3-release-admin` in an independent worktree. ## Implementation boundary

- Migration 0022 adds an immutable success ledger for `validation.start` and `release.publish`. Existing migration bytes 0001–0021 are unchanged. `maintenance.begin` continues to use its earlier durable request ledger.
- `effectiveValidationProof` is the common persisted Node × Game × Preset proof predicate used by the scheduler, release publication, and Admin reopen actions. It checks the current Run, maintenance epoch, content identity and fact revision, template binding identity/generation and fact revision, current complete inventory with no unaccounted instances, Node compatibility/capability/freshness, and Ready/JoinInfo evidence.
- The scheduler locks Game/Preset and Node in the established order, checks proof in the reservation transaction, snapshots the formal content/template, and freezes the v1.0.2 Controller capability and expected machine identity on the player create Job. Legacy Presets retain legacy Jobs.
- `release.publish` performs expected-old CAS, ownership and proof checks, immutable release/history insertion, formal pointer and contract updates, and Audit in one transaction. The first release and any content pointer change require a plan for every current Preset; a complete all-paused plan may publish without admitting any player. Later template-only publication can target one Preset. Rollback creates a new release and requires current proof; no historical row is edited.
- Admin routes expose scoped maintenance, validation start/confirm/stop and detail, release publish and detail. The server finalizes terminal Runs after formal stop and full reclaim. Reads do not finalize Runs. I3 errors are typed; raw SQL errors are not sent to Web.
- Admin Web shows separate per-Preset proof and release plans, machine facts, inventory, Run lifecycle, JoinInfo, and rollback history. Legacy content publication is visible only for legacy games. Controller reconcile completion is displayed separately from current machine proof.
- Operations documents cover the L-D3 fail-closed operator path, Reviewer A L-01 reconcile distinction, and L-D2/L-D4 data-directory requirements. The UI does not invoke Content Tool, d2core, shell commands, or a force-release action.

- A disposable local PostgreSQL 16 cluster runs full `internal/platform/store` and `internal/platform/httpapi` integration suites. I3 regression tests cover no PASS, first release, content change, template-only publication, rollback, request idempotency, cross-game IDs, the migration 21→22 rerun, and shared proof invalidation after epoch, content fact, template binding/fact, and inventory drift. The adjusted legacy-versus-validation last-slot race keeps its legacy fixture explicit.
