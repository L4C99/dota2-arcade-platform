## Node API 与逐请求执行 fence

`/api/node/v1` 和 `APIVersion=1` 保持不变。新字段均为 additive；旧 heartbeat、legacy Job 请求体与严格 JSON 解码可用，因此升级顺序是 New Platform → New Controller。旧 Controller 不持有 session 时只可读取与执行 `legacy_v1`；Store 在 open/claim/GET/active Allocation 查询中先按不可变 `required_capability` 过滤，直接 prepare/report/instance fact 在读取或写入前检查当前请求。

新 Controller 生成进程本地随机 ID，以 Node Secret 认证请求 `POST /session`。Platform 发放 32 字节随机、base64url opaque token，仅在内存保存 SHA-256 digest、Node、进程 ID、三个 capability 与 90 秒过期时间；不写 DB/Audit、URL 或普通日志。Controller token 仅存在进程内存，45 秒内到期时续约。新 session 取代同 Node 旧 session；Platform 重启使所有 session 失效。token 比较使用常时比较。Node Secret 和 heartbeat capability 字段都不构成执行授权。

fence 覆盖 open jobs、普通/independent-stop claim、单 Job GET、prepare、report、active Allocations、instance fact、inventory 与 session check。受保护 HTTP 请求持有读锁至处理完成；session 替换持有写锁，避免旧 token 在替换完成后继续提交该 HTTP 请求。无权访问 v1.0.2 Job/Allocation 返回 404（列表过滤），inventory/session check 返回 403。session 丢失不修改 Job、Allocation 或 ValidationRun，容量继续占用。新 Controller 获取新 session 后沿原 durable Job 恢复。

Controller 在 v1.0.2 Job 开始处理及每次本地 core Create/Stop 前调用 `/session/check`。这个跨 Platform 与本地 core 的 preflight 检查不是分布式原子事务；并发运行两个*新版* Controller、恰在检查响应与本地 core 调用之间更换 session 的极窄竞争，留给独立审查重点确认。旧 Controller 没有新 Job 的任何 payload，也没有新版 core 执行路径。

## Template 与 content proof

可选 `templateManifests` 不改变旧 `templateBindings`。每个 v1.0.2 binding 指明只读 `versionRoot`、绝对 `templatePath` 与显式静态依赖列表。`template-manifest-sha256-v1` 对 canonical path、template 原始字节 SHA-256/长度、按 canonical path 排序的依赖 path/长度/SHA-256 使用大端 64 位长度前缀编码后做 SHA-256；编码及排序与 map 遍历顺序无关。template JSON 本身覆盖 arguments/cfg/readiness；d2core 临时 cfg、Dota 整体和 core binary 不在 manifest 内。

缺少 manifest/依赖、相对或非 ASCII 路径、越出受管 root、重复路径或同一文件身份、不可解析 symlink/junction、可写文件或目录、hash 期间文件身份/长度/mtime 变化均不给 confirmed。heartbeat `templateFacts` 只来自本机 manifest；Store 只有最终事实 identity/state 变化才递增 I1 `template_fact_revision`。旧 heartbeat 缺少 facts 仍合法，缺失事实不能延续旧 confirmed。

NodeJob 的预期 fingerprint、binding generation、workshop ID、content version ID、VPK SHA-256 在创建时固化于不可变 Job 列。Controller 用本机当前 link/metadata/VPK 原始字节复读 content identity，v1.0.2 prepare 提交 manifest algorithm 和 observed fingerprint；Store 与固化预期比较。首次 freeze 固定 d2core key、template path、port、请求 fingerprint、manifest algorithm、observed fingerprint 与 capability；不同的重复 prepare 返回 409。第一次 core Create 前再次核对 manifest/content/path。此时不符为结构化 `rejected_no_effect`，无 core call；可能调用 core 后的漂移保持 `unknown` 与原 key/容量，由原 Job reconciliation。d2core history 过期仍 fail closed。

## Inventory、恢复与资源语义

一个 Controller cycle 取得一次经过完整解码与实例字段/重复 ID 校验的 d2core List；为该次读取生成唯一随机 scan ID。`POST /inventory` 写入 I1 inventory ledger，成功的空 List 才是 `complete=true, instances=[]`。List 失败、null、截断或无效实例均为 unknown，不能伪零实例。只报告尚未达到 `reclaimed/stopped/complete` 的实例。随后 heartbeat 引用同一 scan ID 与 confirmed/unknown；Store 的 reserve/PASS gate 要求持久化的 complete report、相同 confirmed scan、未过期且 unaccounted=0。重复 scan ID 安全冲突。归属由 Platform 的 Job/Allocation/immutable instance ledger 算出，integration-only、未知或 terminal Allocation 仍活跃实例都算 unaccounted，并阻塞 machine proof。

同一 cycle 的 List 同时供 inventory、open Job recovery 与新 claim 使用。旧 Controller 可处理 legacy Job；已 freeze 的 v1.0.2 create 及 formal stop 对它不可见、不可 claim/GET/prepare/report/提交 instance fact。新 Controller 重新拿 session 后读取同一 Job 与 frozen key/path/port/fingerprint；Create 重试仅用原请求，Stop 沿原 instance 与 formal stop Job。超时/失联为 unknown，full reclaim 前不释放容量；不使用 core restart。
