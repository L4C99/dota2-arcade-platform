# P5B Content Tool and rolling release — PASS

## Implemented

- Offline `content-tool status/prepare/switch/rollback` keeps immutable VPK releases and metadata outside the live addon directory. Linux uses a whole-directory symlink; Windows uses a directory Junction. A transition journal and explicit recovery path protect interrupted switches. The tool does not call Platform, Controller or d2core.
- Controller reads the actual linked directory and VPK SHA256, reporting `unknown` when it cannot confirm the local content.
- Local Windows tests exercise prepare, idempotence, immutable-version rejection, switch, rollback, Junction readback, interrupted transition recovery and lock handling. GitHub Actions [run 36231578148](https://github.com/L4C99/dota2-arcade-platform/actions/runs/36231578148) passed Linux and Windows Go jobs, including the same Content Tool tests on both operating systems with disposable test files.

## Real two-node `3564393242` legacy rollout

- The old game and its `n6` preset were set to maintenance, and the Linux old-game Binding was closed. With no occupied Linux Allocation, the node was Drained. Content Tool switched only the old Workshop link from `p1-test-v1` to the prepared immutable `p5-3564393242-legacy` release. Controller independently reported the new version and SHA256 `27b4b93824c2a5ebc96ad9986954e9e6602981800085dee3805739afb4249c0c`. A fixed-d2core instance using the formal old-game template reached full Ready; the owner joined through the Linux public game address and confirmed normal gameplay. After explicit test completion it was stopped, reached `reclaimed/stopped/complete`, and disappeared from the instance list. Admin `content.validate` recorded the human result on the drained empty node; Controller reconciliation generation 7/7 completed before Resume.
- While global current was still `p1-test-v1`, an ordinary player API request created a Windows Allocation on the old version and reached Ready and private JoinInfo. Its request and Allocation remained `running` with `p1-test-v1` after the global target changed. Linux was Resumed, then audited `content.publish` changed current to `p5-3564393242-legacy` **while the Linux Binding was still closed**. Readback immediately after publication confirmed the Windows old Allocation was unchanged, Windows still reported P1, and Linux reported legacy. The Linux Binding and old-game admission were opened afterward. A new automatic player request snapshotted legacy, selected only Linux, reached Ready/JoinInfo, and fully reclaimed. The Windows old Allocation continued running throughout this transition, then a formal Admin stop Job fully reclaimed it. This demonstrates no forced stop, no history rewrite and no same-node active version hot switch.
- With the Windows node empty, its old-game Binding was closed and the node Drained. Content Tool switched the Windows Junction to the same prepared legacy release; Controller readback confirmed its version and exact digest. A fixed-d2core instance using the formal Windows old-game template reached full Ready, including Steam login success. The owner joined through the local VM private address and confirmed normal gameplay. After explicit completion the instance was stopped and fully reclaimed; Admin `content.validate` recorded the Windows human result, and Controller reconciliation generation 4/4 completed before Resume. The Windows old-game Binding was opened last. A normal player request manually selecting Windows then snapshotted legacy, reached Ready and private JoinInfo, and fully reclaimed.
- Final readback: both nodes are Resumed, fresh and compatible; both report `p5-3564393242-legacy` with matching SHA and accept old-game allocations; `ArcadeGame.current_content_version_id` is the same legacy ID. Both Content Tools retain immutable `p1-test-v1` and legacy releases, with P1 as the previous rollback target. No occupied Allocation, open NodeJob, or d2core instance remains. Temporary Admin accounts used for the rollout were disabled. Existing automated PostgreSQL tests cover the waiting-request version switch and Allocation snapshot immutability; the real rollout independently confirmed old active Allocation preservation and new-node version matching.

## Scope limits

- The Windows VM was reached from the owner's local Dota client, but its private address has no verified public player route. Its *new-game* Binding remains closed; P5B rolled the existing game's second ContentVersion. A live waiting request spanning a global version change was not staged; that behavior passed the PostgreSQL integration suite. No production rollout is claimed.
